# 0013 底座知识库由 survey 角色摸底产出，挂底座受保护，每个角色先读

日期：2026-09-23

## 问题

三层体系（要做什么 / 怎么做 / 做没做对）里，"底座已经能做什么、新功能该怎么加"没有显式载体。product 角色靠自己翻代码起草，implement 靠一份手写指南，容易重复建设或绕开既有积木，实现不符合底座要求。

## 决定

- 新增 `survey` 角色：只读探索 README、构建文件、入口与配置、请求链路、模块职责、接口、扩展机制、可复用积木、已有测试，产出固定八份 Markdown（README、modules、architecture、extension、api、capabilities、building-blocks、testing）。
- 产物写到 `openspec/foundation/`，引擎校验（Markdown、路径限定、八份齐全、不含凭证样式内容）后自动开 BASE 提案，经 `base-update` 进入受保护的底座。
- 之后每个角色的 payload 带 `foundation`，说明要求先读；product 不重复建设、沿用既有需求标题，implement 按扩展机制放文件并复用积木，review 把重写积木记为 finding。
- 知识库跟着底座版本走：上游同步或改变机制的 BASE 迭代后重新 survey。

## 理由

- 以仓库文件为载体，适配器中立、可审计、可进 BASE 迭代；技能（Claude 专属）只能作为指向它的薄壳。
- 用代理摸底而不是脚本索引：模块架构、运行机制、扩展机制需要理解，不是 grep 能得到的；脚本只能做接口清单这类事实。
- 三个接触点缺一不可：建（跟底座版本）、读（进每个角色的请求）、核（review 对照）。

## 代价

- 摸底一次的成本与一个大变更的 product 角色同量级；产物需要人审一遍。
- 知识库可能过时，但过时的知识库随底座版本可追溯，比各代理各自理解要好。
