## 1. 目标与边界

代理每次冷启动。仓库里踩过的坑、底座知识库里的错误结论，现在只能靠人记住、下次再说一遍。本期让这些东西有固定的落点、有人批准、能在下一个相关变更里自动送到对的角色面前，并且报告能说清"送了什么、代理说用了什么"。

本期交付：

1. 经验条目（`openspec/lessons/`）：格式、校验器、核心层与普通层、受保护；
2. 取用：按角色、路径、状态筛选注入，核心层始终在场；上下文清单记录交付了哪些条目；
3. 被读的证据：代理回报 `lessons_used`，报告对照"提供 / 声称使用"；
4. 积累：收尾时只在出过问题的变更上，由 review 的复盘模式（只读）提议经验草案，优先更新已有条目；
5. 按强度分流落点：prose → 经验条目；knowledge → 底座知识库；check → `check_commands`（先证明会红）；
6. 统一草案目录与审批：`.storyloop/drafts/<种类>/<id>/` + `approve --draft`；多落点原子写入，失败回滚；
7. 事实层勘误：任何角色可当场提议，不需要出过问题；
8. 新鲜度：作用范围内文件在记录之后被改过即视为 `needs-review`；提供后同类失败仍复发的，提示升级为检查；
9. 底座原则带版本号和变更记录；收尾时检查是否引入了知识库没覆盖的新概念。

不做：

- 知识库补充（survey 技能包必含节、来源状态、随机抽检），按 §13 延后到本子项目完成之后；
- 向量检索（§10.6 已定，重新评估信号见 §6.4）；
- `config` 强度的自动落地（见 Q6）；
- 把 `smoke-propose`/`smoke-apply`、`base-propose` 的存储迁到统一目录：保留原命令和原位置，只让新种类走统一审批（见 Q1）；
- 从工具调用轨迹证明"代理实际读了"：引擎拿不到可信轨迹，`lessons_used` 是代理声称，报告照此标注；
- 跨仓库的经验晋升（延后项，触发信号：同一技术栈有两个以上仓库在用）。

## 3. 方案选择

经验是"人批准过的、关于这个仓库的判断"，和合同一样是代理的输入而不是代理的产物。所以：代理只能提议（写草案），人批准后落地；运行中的取用以合同提交上的经验为准，运行期间对经验的改动不影响这次运行。

被否决的做法：

- **经验也走 BASE 提案 + `base-update`**：每条经验都要跑一次回归门，太重；经验不改变代码行为，回归门证明不了它对不对。经验用自己的保护摘要（§10.1 原文）。
- **复盘由 implement 角色做**：它刚写完代码，倾向于为自己辩护；review 角色已经独立读过全过程，且复盘模式只读。
- **每个变更都复盘**：顺利完成的变更没有新信息，只会产生噪声条目，违反入选标准。

## 4. 经验条目

### 4.1 文件格式

每条一个文件 `openspec/lessons/L-0007.md`。开头是元数据块，后面是正文：

```markdown
---
id: "L-0007"
summary: "WSL2 下时钟回拨会让雪花 ID 报错，验收前先校时"
tier: "normal"
scope: ["backend/**"]
roles: ["acceptance", "implement"]
strength: "prose"
source: "FEAT-20260920-001"
baseline_commit: "3f2a9c1"
status: "active"
updated_at: "2026-09-21"
supersedes: []
landings: []
---

正文：现象、原因、该怎么做、怎么确认。删掉这条，下一个 AI 冷读代码会得出什么错误结论。
```

元数据块每行 `键: 值`，值必须是合法 JSON（见 Q2）。字段：

| 字段 | 约束 |
|---|---|
| `id` | `L-` 加四位以上数字，与文件名一致，全局唯一 |
| `summary` | 一行，≤ 120 字符 |
| `tier` | `core` / `normal` |
| `scope` | 非空 glob 列表，语义同 2b 的 forbidden 路径（`/**` 递归）；`["**"]` 表示全仓库 |
| `roles` | 非空，取值为现有角色名 |
| `strength` | `check` / `config` / `knowledge` / `prose` |
| `source` | 产生它的变更 ID，或 `manual` |
| `baseline_commit` | 记录时的提交；新鲜度的起点 |
| `status` | `active` / `needs-review` / `retired` |
| `updated_at` | ISO 日期 |
| `supersedes` | 被它取代的条目 ID（那些条目必须是 `retired`） |
| `landings` | 非 prose 强度时必填：落点引用，如 `{"kind":"check_command","name":"clock-sync"}`、`{"kind":"foundation","path":"openspec/foundation/runtime.md","anchor":"..."}` |

正文 ≤ 4 KB。核心层所有条目正文合计 ≤ 4 KB（见 Q4）。

**为什么 check/knowledge 强度也留一条经验文件：** 落点（`check_commands`、知识库）只说"现在是什么"，经验文件记录"为什么、从哪个变更来、作用范围"，新鲜度和复发统计都挂在它上面。

### 4.2 校验器

一个校验函数，手工编辑、草案审批、取用前三处共用：字段与取值、ID 与文件名一致、ID 唯一、`supersedes` 指向的条目已退休、`landings` 指向的落点存在、核心层总量上限。校验失败：审批拒绝；取用时整个经验层不注入并在调用记录与报告里写明原因（不阻断运行，见 Q3）。

### 4.3 保护

- 边界审计增加类别 `LESSON_PROTECTED`：运行中任何角色写 `openspec/lessons/**` 都是越界，处理同 `CONTRACT_PROTECTED`。
- `approve` 冻结合同时，同时记录合同提交上 `openspec/lessons/` 的树摘要到运行状态 `lessons_digest`；取用一律从合同提交读（`git show <contract_commit>:openspec/lessons/...`），不读工作区。
- 经验的改动只经 `approve --draft` 或人手工提交；手工提交的条目在下一次取用前过校验器。

## 5. 取用

### 5.1 注入

在 `project_agents._invoke_once` 注入 `payload.foundation` 的同一位置加 `payload.lessons`（survey 与复盘调用除外）：

```json
{
  "lessons": {
    "core": [{"id": "L-0001", "summary": "...", "body": "...", "path": "openspec/lessons/L-0001.md"}],
    "relevant": [{"id": "L-0007", "summary": "...", "path": "openspec/lessons/L-0007.md", "status": "active"}],
    "omitted": 3
  }
}
```

1. 核心层：`status=active` 的全部注入，带正文；不占下面的名额。
2. 普通层筛选：`status` 不为 `retired`；`roles` 含当前角色；`scope` 与本次路径集合有交集。
3. 排序：`active` 在前、`needs-review` 在后；同状态内 prose > knowledge > check > config（越弱越需要读，见 Q5），再按 `updated_at` 新的在前。
4. 最多 10 条，只给摘要和路径；超出的只报数量。

本次路径集合（Q5）：2b 冻结在路由状态里的评估范围 `assessment.scope.touched` ∪ `assessment.scope.creates` ∪ 本轮之前已产生的 diff（相对 `source_head`）。都为空时，只匹配 `scope` 为 `["**"]` 的条目。

角色说明（`role_instructions.py`）增加一句：`payload.lessons` 是人批准过的仓库经验；核心层必须遵守；相关条目按需打开路径阅读；在回答里用 `lessons_used` 写明用到了哪几条、怎么用的。

### 5.2 被读的证据

- 所有角色的回答 schema 增加可选字段 `lessons_used: [{id, how}]`（`how` ≤ 200 字符）。
- 上下文清单（`call_context`）增加 `lessons: [{path, sha256}]`，与 foundation 同样只记交付的引用和摘要。
- 校验：`lessons_used` 里的 ID 必须在本次提供的列表里；不在的记为"声称使用了未提供的条目"，不拒绝回答，报告里标出。
- 报告（子项目 3 的第 5 节，调用来源）每次调用增加"经验：提供 N 条 / 声称使用 M 条"，并列出 ID；第 3 节给本变更汇总。措辞写"代理声称使用"，不写"已读"。

### 5.3 新鲜度

- **计算而不是改文件**：取用时对每条 `active` 条目算 `git log <baseline_commit>..<contract_commit> -- <scope>`，有提交即视为 `needs-review`，按 §5.1 排在后面，并在注入时带上 `"status": "needs-review"`。文件里的 `status` 只由人改（见 Q7）。
- `base-update` 成功后输出受影响条目的清单（作用范围与本次底座改动有交集的）。
- `storyloop lessons PROJECT` 列出全部条目及计算后的状态；`--confirm <ID>` 把 `baseline_commit` 更新到当前 HEAD 并提交；`--retire <ID> --reason <理由>` 退休条目并提交。两者都走校验器。

### 5.4 复发与升级提示

- **同类失败**：口径用 2a 的失败归属与特征——同一 `attribution` 且失败特征的 `target|criterion|文件` 落在该条目 `scope` 内。
- 某条目在一次调用中被提供，而该次调用所在轮次仍以同类失败结束，记一次复发（运行状态 `lessons_recurrence`）。
- 复发 ≥ 2 次（跨变更累计，统计在 `.storyloop/state/lessons.json`）的条目：复盘时要求复盘模式提议把它升级为 check；`lessons` 命令和报告里提示"建议升级为检查"。
- 向量检索的重新评估信号（§10.6）在 `lessons` 命令输出里给出：条目数、过去 30 个变更中"提供后复发"的比例，超过 200 条或 30% 时提示。

## 6. 积累

### 6.1 触发与问题信号

收尾时（运行到 `PASSED` 之后，回执完成之后）检查本变更是否出现过以下任一信号，有则发起复盘调用：

| 信号 | 来源 |
|---|---|
| 失败后修好的尝试 | 运行状态 `failures[]` 非空且最终 `PASSED` |
| `acceptance-repair` | 运行状态 `repairs[]` 非空 |
| `reset` | 运行状态 `resets[]` 非空 |
| 反复出现的审查发现 | 同一审查发现身份（2a `failure_attribution._review_identity` 口径）出现 ≥ 2 轮 |
| 能推广的回答 | `answers` 中由人回答的问题（是否可推广由复盘模式判断） |
| `NEEDS_SPEC_FIX` | 本变更或被它 supersede 的前一个变更停在过这里 |
| 提供后复发 | §5.4 记到的复发 |

没有信号就不复盘，运行状态记 `lessons.retrospective: "SKIPPED_NO_SIGNAL"`。

另提供手动入口 `storyloop lessons-propose PROJECT --change <ID>`：对已 `PASSED`、`SUPERSEDED` 或停在终态的变更补做复盘（例如被作废的变更里踩到的坑）。

### 6.2 复盘模式

- 角色 `review`，模式 `retrospective`，只读（沿用 4 的中间防线与可写范围：可写范围为空）。
- 输入：信号摘要（每条信号指向运行状态、调用记录、报告的位置）、现有全部经验条目的摘要与路径、知识库文档清单、原则清单。
- 输出（新 schema `retrospective.v1`）：

```json
{
  "lessons": [{"action": "create|update|retire", "target": "L-0007 或 null", "entry": {...元数据...}, "body": "...", "why_needed": "删掉这条，下一个 AI 会……", "evidence": ["path:line"]}],
  "errata": [...同 §7 ...],
  "uncovered_concepts": [{"concept": "...", "evidence": ["path:line"], "suggested_document": "openspec/foundation/xxx.md"}],
  "nothing_to_learn": "没有提议时说明原因"
}
```

- 规则写进角色说明：优先更新已有条目；每次最多 3 条；`why_needed` 回答不了入选标准的不提；复发 ≥ 2 的条目必须给出升级为 check 的提议或说明为什么做不到。
- 成本：记入本变更的账本，受 4 的失控上限约束；到上限则跳过复盘并记 `SKIPPED_COST_LIMIT`。复盘调用失败不改变 `PASSED`，记 `FAILED` 和原因，可用 `lessons-propose` 重试（见 Q8）。
- 引擎校验后，每条提议写成一个草案：`.storyloop/drafts/lesson/<draft-id>/`（`draft.json` + `body.md`），勘误写到 `drafts/errata/`，`uncovered_concepts` 写成 knowledge 强度的经验草案。

### 6.3 底座原则

`openspec/principles.json` 增加 `version`（语义化）与 `changelog: [{version, date, change, source}]`。复盘可以提议原则修订，落成 knowledge 强度草案、落点为 principles；审批后照旧经 BASE 提案生效。能写成检查的原则，提议时一并给出 check 落点。

## 7. 事实层勘误

- 所有角色的回答 schema 增加可选字段 `errata: [{document, claim, correction, evidence: ["path:line"]}]`，任何调用都可以提，不需要"出过问题"。
- `document` 必须是 `openspec/foundation/` 下存在的文件；`claim` 必须是该文件里能找到的原文片段（精确子串）；`evidence` 用 2a 事实记录的位置校验。不通过的整条丢弃，调用记录里写明原因。
- 通过的写成 `drafts/errata/<draft-id>/`，`next`/`status` 提示有待批勘误，不中断运行。
- 审批后的落地方式（Q9）：不改 survey 写的原文，在 `openspec/foundation/errata.md` 追加条目 `E-0003`（被推翻的原文、新结论、证据、来源）；`foundation_payload` 把 `errata.md` 排在文档清单第一位，角色说明写明"勘误优先于原文"。原文所在段落不动，由下一次 survey 重写时吸收。
- 改知识库属于底座改动：审批写入后自动开 BASE 提案，人执行 `base-update` 后生效（与 `skills` 命令现有做法一致）。

## 8. 统一草案与审批

### 8.1 目录与种类

```
.storyloop/drafts/
  <CHANGE-ID>/          变更草案（现状，不动）
  smoke/<CHANGE-ID>/    系统冒烟草案（现状，不动；smoke-apply 照旧）
  lesson/<draft-id>/    本期新增
  errata/<draft-id>/    本期新增
```

`draft-id` 形如 `D-<来源变更ID>-<序号>`；每个草案有 `draft.json`：`kind`、`created_at`、`source`、`proposer`（调用 ID）、`payload`、`status`（`pending` / `approved` / `rejected`）。

### 8.2 命令

| 命令 | 作用 |
|---|---|
| `storyloop drafts PROJECT [--json]` | 列出全部待批草案（含现有变更与冒烟草案，只读汇总） |
| `storyloop approve PROJECT --draft lesson/<id>` | 审批经验草案，按强度落地 |
| `storyloop approve PROJECT --draft errata/<id>` | 审批勘误 |
| `storyloop drafts PROJECT --reject <kind>/<id> --reason <理由>` | 驳回，草案保留并标 `rejected` |
| `storyloop lessons PROJECT [--confirm ID \| --retire ID --reason ...]` | 见 §5.3 |
| `storyloop lessons-propose PROJECT --change ID` | 见 §6.1 |

`approve PROJECT <CHANGE-ID>` 的现有用法不变。人在批准前可以直接编辑草案的 `body.md` 与 `draft.json`；审批时重新过校验器。

### 8.3 按强度落地与原子性

| 强度 | 落地 | 之后 |
|---|---|---|
| prose | 写 `openspec/lessons/L-xxxx.md` | 一个提交 |
| knowledge | 写经验文件 + 改 `openspec/foundation/` 或 `principles.json` | 一个提交，自动开 BASE 提案，`base-update` 后生效 |
| check | 写经验文件 + 在 `profile.check_commands` 加命令；**先证明会红**：在来源变更的合同提交上跑必须失败，在当前 HEAD 上跑必须通过 | 一个提交，自动开 BASE 提案 |
| config | 本期不自动落地：审批时拒绝，提示改为 prose 并人工改配置（Q6） | — |
| 勘误 | 追加 `errata.md` | 一个提交，自动开 BASE 提案 |

前置条件：当前分支是源分支（与 2a 新运行的源分支检查同一口径）、工作区干净、没有运行中的变更锁。

原子性：所有落点先写到临时位置并校验，全部通过后一次性移入并提交；任一步失败（校验、先证明会红、提交）则删除新文件、恢复被改文件、不留提交，草案保持 `pending` 并记录失败原因。开 BASE 提案失败时回退该提交（`git reset --hard` 仅限本命令刚创建的那个提交，且执行前确认 HEAD 就是它）。

提交作者用仓库身份，信息 `chore(lessons): <摘要>` / `docs(foundation): 勘误 E-xxxx`。

## 9. 报告与可观测
