# 验证入口、评测底座与知识维护设计

日期：2026-11-08。状态：设计已由人批准；本文只定义后续实现合同，不宣称评测已运行。依据：共享工作区 `storyloop/research_notes/HelixHarness调研.md`、`storyloop-dogfood3-findings.md:89-146`，以及 [HelixHarness 源码](https://github.com/didi/helixharness)。阶段顺序见[路线图](../../roadmap.md)。

## 1. 目标和归类边界

先让关键流程可比较地跑通：把公共验证入口固定在合同里，让判据、方案和审查核对同一个入口；用冻结 Case 检验非例行人工是否下降。dogfood7/8/11 的多次修复表明，问题常出在验收用例所调用的入口与方案改动路径错位，以及同一 AC 被逐轮追问，而不是缺少更多审查轮次（`storyloop-dogfood3-findings.md:89-119,137-146`）。

满足以下任一条件就进引擎：违反会造成误判通过、越界或数据损坏；能确定性检查；改变状态流转或恢复；属于跨角色契约；属于评测度量。其余方法、经验和判断质量放入按 `roles:` 挂载的技能。引擎只验证声明、引用、边界和状态，不用字符串相似度代替语义判断。现有技能加载锚点：`storyloop/project_agents.py:90-98`；`storyloop/skills/oracle-craft/SKILL.md:1-17`。

| 项目 | 归类与引擎检查 | 技能指导及角色 |
|---|---|---|
| 需求决策树 | 技能；合同现有字段、批准门继续由引擎校验 | `spec-craft`：价值、例子、未决前沿、验证入口由人确认；`product` |

| TDD | 技能；保留现有 RED/GREEN 与受保护套件门，不另设形式门 | `tdd`：只在已确认 seam 上测，先复现再最小实现；`implement, characterize` |

## 2. 故事级验证入口合同

选**故事级** `verification_entries`，每个故事可列多个入口；AC 不重复声明入口，只由测试引用。理由：同一 CLI/HTTP/公共函数通常覆盖多个 AC，入口身份是故事级跨角色约定；若同一故事有不同外部行为，列多个 ID 即可。`independent_test` 保留作说明，不再充当可核对的入口（现状：`storyloop/product_contract.py:212-225`、`storyloop/requirement_checklist.py:35-43`）。

```json
{
  "stories": [{
    "id": "S-1",
    "verification_entries": [{
      "id": "VE-CLI",
      "kind": "cli",
      "locator": "storyloop run <project> --change <id>",
      "observable": "结构化停点 JSON 的 status/next",
      "reason": "用户可调用的公开命令"
    }],
    "acceptance": [{"id": "AC-1", "kind": "automated", "given": "...", "when": "...", "then": "..."}]
  }]
}
```

`kind` 限 `cli|public_function|stop_json|http|other`；`id` 在单个合同内唯一，`locator/observable/reason` 非空。`locator` 是公共调用标识，不是任意可执行 shell 文本；不得据此直接运行。新合同须为每个非 BASE 故事声明至少一个入口。`product_contract.py:76-106,212-225` 与 `role_schemas.py:71-78` 同步接受字段；`requirement_checklist.py:24-55` 在批准前以 error 拦缺失。BASE 无故事（`product_contract.py:93-95`），不适用。

验收 manifest 的每个 test 增 `entry_ids: ["VE-CLI"]`，非空且只能引用其 `criteria` 所属故事的入口；跨故事测试可引用各相关故事入口。若一个 test 声明多个入口，必须各有实际断言，review 检查，不能仅靠 ID 冒充覆盖。接入 `role_schemas.py:51-53,143-145` 与 `smoke.py:131-171`；原有 AC 覆盖、快重档、RED 规则保持。

方案 `routing-plan.json` 的选定 option 增 `entry_paths: [{"entry_id":"VE-CLI","criterion_ids":["AC-1"],"path":"storyloop/cli.py","via":"dispatch→run"}]`：至少覆盖每个自动 AC 所用入口，`path` 必须在方案 `touched/creates` 中，`via` 解释入口到改动点的链。接入 `role_schemas.py:101-115`、`planning.py:27-65`；轻档自动生成方案也必须填或显式转人工设计。`consistency.py:38-71,140-150` 的重档审查按合同入口、manifest test 引用、方案 `entry_paths` 三方核对调用链；引擎确定性校验 ID、AC、路径关系，review 判断是否真经过该入口。判据错误仍走 `ORACLE_DEFECT`，方案错误走 `DESIGN_REVISION_REQUIRED`，合同入口错误走 `NEEDS_SPEC_FIX`（`consistency.py:28-35`）。

RuoYi 示例：`{"id":"VE-HTTP","kind":"http","locator":"POST /api/system/user","observable":"状态码、响应 code 与持久化结果","reason":"业务公开 HTTP API"}`；测试经 HTTP 调用，方案写 `Controller→Service→Mapper` 到具体改动文件。StoryLoop 自身优先 `storyloop` CLI、`storyloop run` 停点 JSON；只有确无公共入口时才将稳定公共函数列为入口，并写明理由。不要把私有实现函数、mock 或文件存在性当作行为入口。选择步骤借鉴 `helixharness/workflows/single/propose.md:200-246` Testing Decisions 与 `helixharness/skills/tdd/SKILL.md:17-35`。

**兼容**：以合同内 `verification_entries` 字段存在作为新格式标记；旧合同/旧变更缺字段时按旧规则执行，manifest/plan 不强制新字段，不隐式迁移。新 `change` 起必须写字段，批准时锁定；不得在运行中静默补写旧合同。已有变更若主动升级，必须走合同修订、重新批准和 RED/方案绑定重证；不能只改 manifest。冻结 Case 的**显式 v1→v2 派生**是离线制备新 Case：人重新批准 v2 合同并校准，绝不修改历史变更或 v1 原件；两版本的比较规则见第 5 节。

## 3. 审查意见与收敛

一致性意见和最终 review 意见统一可追踪元组：`{id, criterion_id, target, disposition, blocking, location, evidence, message, required_change}`。`id` 在同一次变更中稳定，例如 `ORACLE-AC-4-01`；同一根因的重审沿用 ID，新根因新 ID。`target` 沿现有 contract/oracle/design（最终 review 可含 implementation）；`location` 须可定位。`MUST_FIX` 为确定的阻断缺陷，`DECISION_NEEDED` 为需人决定且阻断自动流程，`ADVISORY` 为有证据的可选改进。映射：前两者 `blocking=true`，`ADVISORY` 为 `false`；发现 `blocking` 与级别不符时 schema 拒绝。当前只有 `blocking` 的一致性意见与 `blocked|needs_input|coherent` verdict（`role_schemas.py:117-123`、`consistency.py:38-53`），需迁移 validator/stop；仅 advisory 应 `coherent`，decision needed 应 `needs_input` 并展示问题，不得落入 `COHERENT`。最终 review 的 `pass|fail|needs_input` 仍映射为全局结果，不把 advisory 误计失败（`role_schemas.py:158-169`）。

引擎在 run state 保存按 `criterion_id + target=oracle + weakness=criterion_strength` 归一的连续阻断轮数与前轮 finding ID/证据；相邻完整一致性审查中同一 AC 再次被判强度不足，计第二轮。中间一轮不再阻断则清零；方案/判据修订后的重新审查也算新轮，恢复时不得重复计同一次审查。第二轮仍阻断时，下一轮 review **必须**输出完整判据规格：输入、前提、调用入口、期望结果、负例/边界、与已批准合同/方案的对应。缺项或完整规格后的再次同类阻断，复用 `ORACLE_DEFECT` 停点，附 `convergence: {criterion_id, round, finding_ids, missing_spec_fields, exhausted: true}` 和两轮原文；自动循环结束。若根因是方案路径或合同入口，仍分别用 `DESIGN_REVISION_REQUIRED`、`NEEDS_SPEC_FIX`，同样附 convergence 标记。停点 `next` 对判据给 `storyloop acceptance-repair <project> --change <id> --reason <按已批准合同补全判据>`，对方案给 `storyloop run <project> --change <id> --replan --reason <方案修订说明>`，对合同给 `storyloop change <project> --change <id> --message <合同修订说明>`；仅 oracle/contract 审查判定可用 `storyloop run <project> --change <id> --overrule <理由>`。修复理由不得新增合同要求。完整规格给出后仅允许一次定向修复与一次整体重审；仍同类阻断则同一停点交人，不继续自转。人可修订合同/方案、修复验收或明确 overrule，不自动放宽 AC。持久化计数随合同/方案 binding 失效而重置并记录原因；恢复须幂等。

取舍：复用既有停点而不增加 `REVIEW_CONVERGENCE_REQUIRED` 状态。`consistency.py:153-176` 已按 contract/oracle/design 路由到三个停点，`project_loop_failures.py:184-200` 已提供修复与 overrule 入口；只在停点元数据和提示增加收敛上下文即可，避免新增状态枚举、迁移边和恢复分支。`convergence.exhausted` 必须持久化；同一审查结果重放不能自动启动下一轮，也不能重复增加计数。

`#98` 已减少审查噪声、要求一次列出已发现意见并自动补方案证据（`planning.py:68-79`）；此规则补上“同一 AC 逐轮追问”尚未解决的收敛边界，不能退回逐条修复。借鉴 `helixharness/skills/code-review/SKILL.md:89-95,127-136` 的三级分流、稳定 ID、修后整体重审和无进展停止。最小测试：级别/布尔映射，stable ID 跨轮保持，连续两轮/中断恢复/清零，完整规格缺项停点，advisory 不阻断，修后整审。

## 5. L1/L2 评测底座

**L1 单次运行**：复用现有 M1～M10 与 M11 成本（`storyloop/metrics_compute.py:38-56,294-317`；`storyloop/metrics_cost.py:12-86`）。新增事件级人工记录 `kind=contract_approval|design_approval|manual_acceptance|answer|acceptance_repair|replan|overrule|reset|supersede|knowledge_approval`、发生时间、触发停点、change/AC 和来源。规则：已批准合同/方案的例行批准和合同要求的手工验收为例行；纠错、补约束、overrule、reset、重批及非计划问题回答为非例行。`knowledge_approval` 单列为例行知识维护，不混入改动完成门。自动分类有歧义或缺事件证据时 `unknown`，不填零；输出例行/非例行次数、人工等待 wall time、代理执行时间、总 wall time、已知美元成本和覆盖率。现有 M10 只按动作计数，不能直接代表非例行次数。敏感交互内容不入指标。

**L2 冻结 Case**：目录 `bench/cases/<case_id>/v1/` 与 `v2/`，每版各有 `case.json`、`contract.json`、`gold.json`、`checks/`；运行输出 `.storyloop/bench/runs/<run_id>/`（不入源码）。每个 Case 冻结 `repository_id`、`base_commit`、已批准合同的内容哈希、`solution_commit`、验收套件及参考侧单测的哈希、Gold 的 F2P/P2P 检查命令与期望、允许的适配器/模型/预算。F2P 必须在 Base 失败且参考 Solution 通过，P2P 两边通过；预检校验路径与哈希，校准实际执行检查，不能用退出 0 的空命令或“文件存在”替代业务检查。参考 `helixharness-platform/bench/docs/concepts.md:5-15`。参考实现仅用于校准和隐藏检查，不交给参测代理。

①a-2 制备时，先冻结历史 **v1**：原合同无 `verification_entries`，标 `legacy_seam`，供旧引擎 L2 基线对照。再从同一 Case 派生 **v2**：维持相同的需求、`base_commit` 与 `solution_commit`；根据参考 Solution 的实际公开调用链，由人一次性为五份合同逐份补 `verification_entries`，核对各 AC，批准每份精确合同 diff 与入口选择，再冻结批准记录和合同哈希。v2 的 manifest 测试补 `entry_ids`，验收套件因入口或 harness 隔离而改写时单独留来源/差异并重新做 Base/Solution 校准；不得把参考 Solution 交给参测代理。①c 后的五 Case 门**只跑 v2 新格式合同**，因此会实际经过 ①b 的合同、manifest、方案及审查校验。v1 保持原样，不拿 v1 成绩充当 v2 门槛结果。

比较口径：一次 paired Run 的两侧必须使用同一 `case_id + case_version + contract_hash + gold_hash`，且模型、适配器、预算相同，只允许引擎版本不同。v1 只与 v1 比，v2 只与 v2 比；不支持 v2 schema 的旧引擎标 `INCOMPATIBLE`，不计为失败，也不能与 v2 新引擎硬比。v1 与 v2 可并列展示来源和绝对数据，但不得声称其差值是 ①b 的因果收益。要评估 ①b，使用两个都支持 v2 合同的引擎版本作同版对照，并结合 v2 的入口引用/错位检出证据；改 Case 必须升版，旧 Run 不变。

**①a 前置：自举 Case 的 harness 导入隔离。** dogfood11 的验收子进程在候选镜像 cwd 运行，`from storyloop.testing.smoke_harness.v1 import ...` 会优先取 Case base 仓库的旧 `storyloop/testing`，遮蔽参测引擎 helper（`storyloop-dogfood3-findings.md:137-142`）。选择最小的**自举 Case 专用套件规范化＋预检**：v2 中所有 helper 逻辑由受保护 executor 通过 manifest 的 `{storyloop_harness}` 入口执行；该 token 已展开为当前引擎安装包的绝对 launcher 路径及 `python -I -B`（`storyloop/harness_command.py:8-13`），launcher 校验自身模块来源（`storyloop/testing/smoke_harness/launcher.py:9-26`）。候选 subprocess 只运行被测业务 CLI/代码，不导入 `storyloop.testing.smoke_harness`；bench 预检扫描并拒绝自举 Case 中任何仍在候选侧导入 helper 的测试命令/脚本，执行时记录可信 helper 的解析路径和引擎版本，不匹配即 `NOT_COMPARABLE(HARNESS_SHADOWED)`。不删除候选的 `storyloop/testing`，也不全局改 `PYTHONPATH`，以免改变被测源码或普通项目行为。v1 历史合同/套件保持原样，若出现遮蔽则如实标不可比较；v2 经规范化后须在旧 base 与新引擎组合上校准通过。

CLI 设计：`storyloop bench calibrate <case-id> --case-version 2`；`storyloop bench run --suite frozen-v2 --engine-base <sha> --engine-candidate <sha>`；`storyloop bench report <run-id>`（历史对照显式选 `--case-version 1`/`frozen-v1`）。Run 创建时冻结 5 个 Case 的版本/哈希、两个引擎精确 commit、适配器及模型版本、提示/技能版本、预算、评分合同；每个 Case 每侧跑 2 次，隔离副本，顺序交错以减小时间偏差。两侧只有**引擎版本**可不同，业务 Case、模型、适配器、预算相同。模拟人对例行批准自动通过；任何非例行停点记录 `NEEDS_HUMAN` 并结束该次尝试，不生成猜测回答。最终报告保留每次运行状态、首过、非例行停点数/类型、调用数、耗时、已知成本、成本覆盖率和 F2P/P2P 结果；硬检查不通过即未通过，不能用平均分抵消。两次尝试分别列出，并以“两个尝试均满足”判 Case 过门，避免挑最好一次。首批**暂不运行**；阶段①a 实现后才校准并执行。

缺 base/solution、合同批准证据、suite 哈希、隐藏检查、模型/预算锁、费用或耗时记录中影响对应指标的任一项，相关维度记 `NOT_COMPARABLE(reason)`；业务硬门证据缺失则整次尝试不可比较，不当失败或成功。若两侧关键配置不同，整组不可比较；已完整记录的其他维度仍可展示但不得据此声称胜出。Case 改动生成新版本，旧 Run 保持不可变；参考 `helixharness-platform/bench/docs/concepts.md:17-27,48-58`。

**与本设计的差异**（均由人确认或为试跑证据驱动的修复）：

1. **验收来源**：Run 默认 `--suite-source generated`，引擎正常调用 acceptance 生成套件；Case 冻结套件只作隐藏 Gold。`frozen` 模式仅用于隔离评测设计/实现/审查，两种模式不可互比（#113）。
2. **门槛形态**：阶段门按 v2 **base-only** 绝对判定（5 Case 中 ≥4 个两次均 `PASSED` 且 Gold 通过），不需要 paired 对照。
3. **模拟人**：本节 §5 写的"任何非例行停点即结束"与门槛"每次 ≤1 次非例行停点"相矛盾。实现为每次 attempt 执行一次与 CLI 相同的纠正（acceptance-repair / replan / reset），理由为固定文本、不读 Gold，再次非例行停点才 `NEEDS_HUMAN`（#115）。结果比真实人工偏保守。
4. **成本**：Codex 不返回美元成本。缺成本只记 `cost_accounting: UNAVAILABLE`，成本维度单独不可比，不阻断业务判定；调用数和耗时缺失仍阻断（#114）。
5. **新增的引擎机制**（试跑与门槛证据驱动）：harness 用例级诊断与 RED 环境错误的证据分类（#116、#118～#120）；`regression_updates` 受控更新已有测试（#117）；三类确定性验收缺陷自动退回、计为例行（#121）；"准备 / 执行 / 观察"入口规则（#122）；保持性条件的 `entry_paths` 放宽、批准时校验入口覆盖（#123）；RED 前判据强度预审（#124）。
