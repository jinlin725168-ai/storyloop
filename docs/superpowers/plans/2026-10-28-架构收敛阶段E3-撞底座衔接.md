# StoryLoop 架构收敛阶段 E3：撞底座后的衔接实施计划

日期：2026-10-28。基线：`origin/main` 的 `b9e01a3`。依据[阶段 E 设计](../specs/2026-10-21-架构收敛-design.md) §4.2、§11、§12，[E1](2026-10-24-架构收敛阶段E1-base类型与人工通道.md)、[E2a](2026-10-25-架构收敛阶段E2a-代理实现通道.md)与 PR #43、#47 的人审决定。本计划只安排 E3 的最小端到端切片；实施前仍需人评审。

## 目标与边界

一条已批准的真实功能变更在实施时需要改 `pom.xml` 依赖：边界审计停在现有 `BASE_CHANGE_REQUIRED`，自动生成可审批的 `BASE-*` 草案、把原变更记为 `blocked_by`，把本轮写出的底座差异作为**参考**附在提案中，并从原功能分支恢复底座文件。人在已有 E1 human 通道完成 base 到 `PASSED`；源分支更新后，原功能分支以 **merge** 接入新底座，在新底座上重新证 RED、重跑各层，最终原变更也到 `PASSED`。参考差异不自动当作 base 候选，也不代替具名审批、G1/G2 或人工验收。验收必须有一次真实试用的两个 `PASSED` 记录；单元测试和 PR CI 同为必要条件。

沿用 E1/E2a 的恢复边界：合并前中断的 base 尝试作废重来；合并后只按已有 Git 事实、回执、版本与 I8 幂等路径恢复。E3 不改 E2a 的独立 worktree 与威胁模型，不增 OS 隔离，不依赖 E2b 的判据注入方案。只为原变更记录及运行记录增加可选 `blocked_by` 关联/证据字段（`changes.py` 的严格字段校验须同步）；不增加状态枚举、迁移边或旧状态文件迁移。旧的无关联 `BASE_CHANGE_REQUIRED` 仍按原路径处理。

## 第一批：最短可运行链路

1. **撞底座并让出功能分支。** 在 `project_boundaries.py` / `project_loop_failures.py` 复用现有提案、`base_upgrade.py` 的 scope 推导与 `draft_from_proposal`，一次审计只形成一个稳定的 base ID；重复停点不再派生新草案。只针对本批 `foundation`（如 `pom.xml`）：把已审计底座路径的有界差异与来源 commit、路径、摘要作为非权威参考写入提案，由提案摘要绑定草案；草案展示该参考。原变更与运行记录均写 `blocked_by=<BASE-ID>`，并保存提案路径及关联摘要，再停点。对本轮可归属的候选改动保存诊断参考，恢复到功能分支的合同提交树，使工作区干净；无法证明归属、路径是链接、内容超限或出现人的额外改动时，用现有 `WORKSPACE_TAINTED` 停下保留现场，绝不猜测归属后删除。停点提示按现有 CLI 指向草案审批与 human base 通道；CI 特例保留现有人发起提案的要求。
2. **跑完 base，再合并。** 人从已记录的源分支审批并执行 `BASE-*`（默认 human，E1 旧项目补充配置与旧底座绿、审查、人工验收不变）。仅在关联草案及运行均为 `PASSED`、底座版本和源 HEAD 与 base 回执一致、功能分支无未知脏改动时，`_follow_base_upgrade` 才把源分支 merge 到原功能分支；不得 rebase、跳过不相干的底座提交或接受未完成的 base。合并冲突沿用现有 Git/`WORKSPACE_TAINTED` 停点交人处理；不自动清理现场，不引入另一套恢复。
3. **在新底座上重证。** 合并后的树必须仅含原锁定合同、判据和新底座，不能沿用旧实现候选。将该合并提交记为新 `contract_commit`，`source_head` 绑定 base 回执中的新源 HEAD；旧 RED、层级、审查、报告与验收证据失效，现行证据槽位须由新证据替换并保留旧记录供审计。保留原合同、具名批准、预算及失败历史，不把清空旧证据当作成功证明。复用 `_prepare_acceptance`、`run_smoke_isolated` 和现有各层验证，先得到新 RED，再用现有 `begin_attempt` 边从 `BASE_CHANGE_REQUIRED` 进入实施，全部重跑到 `PASSED`，无需新迁移边。如果新底座已满足验收，沿用 `EXISTING_GREEN`；若新 RED 失败原因不明，沿用现有错误停点。旧无 `blocked_by` 运行不改变行为。

## 实施任务与测试顺序

每项先写失败测试、确认红，再改代码、确认绿；每项独立提交。新测试按现有 `tests/suites.py` 登记，不为架构测试加豁免。

| 任务 | 先红的关键断言与位置 | 最小实现与验收 |
|---|---|---|
| T1 草案与停点 | `tests/test_project_boundaries.py`、`tests/test_failure_routing.py`（SAFETY）：撞 `pom.xml` 自动得到唯一可审批草案、参考差异可读且仅供参考、`blocked_by` 与提案同 ID、重复审计不增草案；混入人的改动不清理 | 复用提案/导入函数，限定参考大小与路径；`run_hints.py` / `stop_report.py` 显示关联 ID 与 human 下一步。原 CI/非底座越界测试仍绿 |
| T2 base 完成与合并 | `tests/test_project_loop_resume.py`（SAFETY）：base 未 `PASSED`、版本/回执不符、脏树都不能合并；base 通过后形成双亲 merge，冲突保留现场；旧无关联运行照旧 | 在已有 `_follow_base_upgrade` 附近加具名关联校验和 merge；复用 E1/E2a 的完成事实及锁，不另建恢复入口 |
| T3 重证与真实链路 | `tests/test_project_loop_resume.py`（SAFETY）先断言旧 RED/层/报告不能用于新底座；`tests/test_routing_e2e.py`（END_TO_END）先断言两变更到 `PASSED` 且新 RED、全层证据来自合并后 | 接回 `_prepare_acceptance` 和现有验证链；记录一次**真实** `pom.xml` 依赖变更试用（功能变更、human base、merge、重证、双 `PASSED`），失败如实记载，不以模拟代替 |

每项提交前跑 `ruff check storyloop tests examples`、相关测试与架构零豁免检查；最终跑本机 core、后台 full、PR CI，并在 `docs/validation/` 留下真实试用记录（命令、两变更 ID、提交/证据 ID、结果与限制）。在 PR 描述分开列本机与远程结果。新增测试若明显拖慢 core，记录耗时和归属。

## 与 E2b 并行及后续

可能同改 `project_boundaries.py`、`base_upgrade.py`、`base_execution.py`、`project_loop.py`、`run_guards.py`、`tests/suites.py` 与 base/恢复测试；E3 只改撞底座、关联、合并、重证入口，E2b 的判据路径/注入验证由 E2b 自定。两分支合并时先核对这些文件与测试，再跑 core；不把 E2b 未定接口写进本计划。

后续再处理混合 scope/CI 自动草案、较大或二进制参考、复杂合并冲突的自动续跑、额外恢复与威胁模型加固。E3 第一批不声称完成 E2b 的判据注入跑红，亦不单凭单元测试宣称阶段 E 全部达标。

## 待人决定

- **本轮可归属的功能候选是否保留？** 推荐把差异保存在有界诊断参考后，恢复功能分支到锁定合同树，再跑 base；理由是合并后必须在新底座上重证 RED，保留旧实现会掩盖 RED。若无法证明候选归属，保留现场由人处理。
- **参考差异的承载形式。** 推荐放在提案的可校验、有界附属记录中，草案只引用并展示，合同仍只列批准路径；理由是 `product.base` 当前严格只允许 `scope/paths/must_stay_green`，参考不应改变合同或自动成为实现。
