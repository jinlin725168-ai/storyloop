# StoryLoop 架构收敛阶段 D 实施计划

> **执行要求：** 使用 `executing-plans` 逐任务实施。每个代码任务先写能在旧实现或故意注入的违规上失败的测试，再实现、确认通过、单独提交。阶段 D 可拆为多个实现 PR；本计划先供人评审，批准前不修改生产代码。

**目标：** 消除当前 31 条阶段 D 架构豁免，使底座不导入可变区且底座内部无环，并使 `project_loop.py`、`cli.py` 均少于 450 行，同时保持 CLI、停点、错误码、状态格式和报告行为不变。

**架构：** 把状态格式与纯协议留在底座，把项目上下文组装和策略编排留在可变区；证据内核只核验输入事实，由上层调用方负责烟测、记忆、报告等副作用。新的跨层依赖一律靠传入已计算的值或抽出真正属于底座的格式定义解决，不通过动态导入隐藏依赖。

**技术栈：** Python 标准库、现有 `unittest`/`tests/run.py`、`storyloop/architecture.toml`。

**设计：** `docs/superpowers/specs/2026-10-21-架构收敛-design.md` §5.3、§9.3、§10、§11 阶段 D、§14.1。模块归属以设计职责为准，不为消除边而把业务策略冒充底座。

- 从合并 PR #28 的 `origin/main` 创建独立实现分支；不在共享工作区切分支。每任务中文提交 `<type>(<scope>): <subject>`，作者只用仓库身份 `jinlin725168-ai`，不加 Co-Authored-By。
- 不加入架构豁免，不放宽守卫或改变测试预期来凑绿。每消除一条边，当步删掉对应豁免；新模块当步登记进 `architecture.toml` 和 `docs/modules.md`。
- 阶段 A–D 的“底座”仍只用于静态架构声明；不改用户仓库 `baseline.json`，不实现 base 类型、T6 引擎分离或执行画像。
