# 链路骨架 第 1 批：变更 ID、执行画像、版本快照 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 新建变更的 ID 带上功能短名；每条调用账本记下引擎版本、说明摘要、schema 摘要；每个变更在批准时冻结一份版本快照，报告标出运行中版本是否变化。

**Architecture:** 功能短名由 product 角色在已有的"创建前"调用里提议（合同新增可选字段 `slug`，创建时取走、不进合同指纹），人可以用 `--slug` 或交互确认来改。执行画像在 `telemetry.record_call` 与 `project_agents._execute_call` 两处补齐，都由引擎写入、不采信适配器。版本快照写进批准记录 `approval.versions`，报告通过已有的 `approval` 字段带出，另加一个"版本漂移"小节。

**Tech Stack:** Python 3.11 标准库；`unittest`；现有 `storyloop` 模块。

**Spec:** `docs/superpowers/specs/2026-10-23-链路骨架-design.md`（§5.2 变更 ID、§7 执行画像与版本快照、§11 T3、§12 分批）

## Global Constraints

- 旧格式变更 ID `<前缀>-<YYYYMMDD>-<NNN>` 继续有效；已有状态文件、合同指纹、报告格式的已有字段一律不变，只做增量（设计 §5.2"兼容"）。
- `slug`：3–40 个字符，只含小写字母、数字、连字符，以字母或数字开头和结尾，正则 `^[a-z0-9](?:[a-z0-9-]{1,38}[a-z0-9])$`（设计 §5.2）。
- 执行画像只存摘要，不存说明原文（设计 §7.1）；摘要用 SHA-256 十六进制，与现有技能快照的 `sha256` 一致。
- 执行画像由引擎写入，不采信适配器自报（设计 §7.1）。
- 不引入第三方依赖；单个文件不超过 500 行。
- 改动只落在：`product_contract`、`role_schemas`、`role_instructions`（product 段的输出形状一句）、`changes`、`cli`（参数定义）、`product_cli`、`telemetry`、`telemetry_summary`、`project_agents`、`approvals`、`report_evidence`、`report_markdown`、`storyloop/architecture.toml`（不变量登记）以及测试和文档。分层与豁免守护（`tests/test_architecture.py`）必须保持零豁免。
- commit 格式 `<type>(<scope>): <subject>`，中文；只用仓库用户身份，不加 Co-Authored-By trailer。

## 本计划作出的决定（实现前请评审）

1. **功能短名由 product 角色在创建前提议。** 现在 `change --idea` 先调用 product 角色、再 `create_change`（`product_cli.py`），所以在合同里加一个可选字段 `slug` 即可，不需要额外的调用。`create_change` 把它从合同里取走后再保存，因此它不进合同指纹，以后的修订也改不了 ID。
2. **优先级**：`--slug` 参数 > 交互确认时人输入的值 > product 角色提议的值 > 都没有时退回旧的序号格式。退回旧格式是为了让脚本化测试和 manual 适配器照常工作。
3. **合并时的冲突复核放到第 2 批。** 设计 §5.2 要求创建时和合并时各检查一次；合并时那一次要新增停点，又和需求登记一起检查最合适，所以本批只做创建时的检查。
4. **版本快照写在批准记录里，不进合同指纹。** 设计 §7.2 写的是"锁进合同指纹"。但合同指纹只覆盖产品内容，改它的计算方式会让已批准的旧合同全部变成"过期"。批准记录在控制面里受保护，写入后不再改动，效果相同。
5. **适配器只记名称（已有），不记外部 CLI 的版本。** 目前没有可靠的办法拿到 Codex、Claude Code 的版本号；以后有了再加字段。每次调用的技能快照已有 `name`、`version`、`path`（区分引擎自带还是项目副本）、`sha256`，满足设计 §7.1，不改。
6. **需求地图版本**本批记为 `null`，第 2 批有了地图再填。

## Review Focus

1. 旧格式 ID 的变更（已有的状态文件）照常能修订、批准、运行、出报告：新代码不能假设 ID 一定带短名。→ Task 1 `test_legacy_ids_still_resolve_their_type`、Task 3 `test_approving_a_legacy_change_records_versions`。
2. product 角色返回了不合法的 `slug`（大写、太长、带空格），不应让整次创建失败，而是丢弃它、退回下一优先级。→ Task 1 `test_invalid_proposed_slug_is_ignored`。
3. 同一天同名的变更已经存在（本地状态或 `openspec/changes/` 下已有目录），要报错并说明怎么换名，不能覆盖。→ Task 1 `test_taken_slug_is_refused_with_a_hint`。
4. 跨厂商回退、代理不可用时写的失败账本记录（`cross_vendor.py` 直接调用 `record_call`）也要带引擎版本。→ Task 2 `test_failed_availability_entries_carry_the_engine_version`。
5. 账本里有一部分旧记录没有执行画像（升级前产生的），报告不能报错，也不能把它们当成"版本变化"，而是标为"未知"。→ Task 4 `test_entries_without_profile_are_unknown_not_drift`。

判定规则：没有快照（旧变更），或者账本里所有记录都没有 `engine_version`，返回 `unknown`；出现过的引擎版本里有和快照不同的，或者某次调用的技能 `(name, sha256)` 不在快照里，返回 `changed`；否则 `unchanged`。部分记录没有画像时不算 `changed`，只计入 `unprofiled_calls`。
