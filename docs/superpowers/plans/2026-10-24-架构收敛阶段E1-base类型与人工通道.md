# StoryLoop 架构收敛阶段 E1：base 类型与人工实现通道实施计划

> **执行要求：** 本文供人评审。批准并且链路骨架第 1 批合入后，另开实现分支逐任务执行；每个代码任务先写失败测试，确认失败原因，再实现、确认通过、单独提交。本 PR 只交付计划。

**目标：** 让人工提交的 base 改动从草案、批准、旧底座 G1、验证、人验收、合并到版本回执经过同一生命周期；现有 BASE 用途及 `base-update` 经此通道，不再直接升级 `baseline.json`。

**设计：** [架构收敛设计](../specs/2026-10-21-架构收敛-design.md) §4.2、§4.3、§6.2、§8、§11、§12 S-4、§13 Q2。E1 只交付已明确允许的人工实现通道。代理实现、改判据后的注入跑红、跨厂商审查及单代理人审替代留 E2；撞底座后的 `blocked_by` 与原变更重证留 E3。E1 不宣称整个阶段 E 或 I13 完成。

**技术栈：** Python 标准库、现有 `unittest`、`tests/run.py`、Git 本地分支。以下接口名称是计划建议，实际签名以实现时的代码为准；偏离须在实现 PR 列明。

## 全局约束

- 实现须从链路骨架第 1 批合入后的 `origin/main` 建独立 worktree。该批正在改 `approvals.py`、`changes.py`、`telemetry.py`，E1 在这三个文件上的设计以合并后的接口复核；不从 PR #37 分支实现 E1。
- 旧 `BASE-*.json` 提案、升级回执、`baseline.json` 历史版本和非 base 合同指纹逐字兼容。只新增可选字段与文件；任何读取新字段的地方先处理旧记录。保留 `base-update` CLI。不得直接改已有用户状态文件做迁移。
- `tests/test_architecture.py` 零豁免；新模块登记 `architecture.toml`、`docs/modules.md`，内核只读磁盘事实，不导入可变区业务。禁止 push、rebase 或改写历史；合并仅本地 merge。所有 base 改动独立提交，不与 feature 混合。
- E1 不开放代理实现：命令显式选择 `--implementer human`，由人提交；默认代理路线在 E2 开通前返回明确的未支持错误。不能为了本批绕过设计的方案批准、最重档位、人工验收和 G2；人工提交的方案由人批准，独立审查由不同的人记录具名结论。跨厂商及其替代规则在 E2 实现，E1 报告标为“人工通道／人工审查”，不得标为“跨厂商通过”。
- 每任务按测试红→最小实现→目标测试绿→架构测试绿→提交。最终后台完整运行 core/full，记录耗时、跳过数与结果；本机与远程 CI 分列。若连续三次修复同一问题仍失败，记录完整报错并停下。

## 评审修订（2026-10-24，以此为准）

人评审后修订下面两条决定；与之冲突的任务描述和测试一律按本节执行。

**修订决定 2（必须保持绿）：**
- 合同值仍固定为 `full_regression`、`system_smoke`、`build` 三项。
- **`full_regression` 默认取项目已经配置的全部测试层**（unit、integration、checks，凡配置了的都要跑，任何一层都不能跳过），不新增 `base_full_commands`。理由：现有 `base-update` 就以这些层作为回归，已接入的项目（如 RuoYi）不必先补配置。
- **`base_build_commands` 是新增的设置键，可以显式写成空列表 `[]`**，表示"本项目没有构建步骤"；此时报告写明"项目声明无构建步骤"，人工验收时可以看到。**缺少这个键**（而不是空列表）时拒绝批准，提示在 `acceptance/storyloop-settings.json` 里加上它。不得用任何命令冒充构建。
- 系统冒烟没有已安装的套件时，照旧不能算通过。
- 接入模板（`onboarding_templates`）生成的 settings 草案加上 `"base_build_commands": []` 和一句注释说明，让新接入的项目由人显式确认。
- 测试相应调整：Task 1 的"无构建配置"改为"缺少 `base_build_commands` 键被拒绝，显式空列表被接受"；Task 2 的绿证据记录实际执行的各测试层与构建命令（可能为空），空构建在证据里写明。

**修订决定 4（人工交互）：**
- **人工通道不调用 design 代理，也不停在 `DESIGN_APPROVAL_REQUIRED`。** 人批准的 base 合同（目标、精确路径、`scope`、必须保持绿的条件）就是方案，批准合同即满足设计 §4.2"方案必须人批准"。
- 批准后 `storyloop run --change <BASE-ID> --implementer human` 建分支、做 G1，然后直接停在 `HUMAN_IMPLEMENTATION_REQUIRED`。
- 代理通道（E2）照常要求 design 方案和人批准。
- 测试相应调整：Task 3 去掉"方案经人批准"的停点断言，改为断言人工通道在 G1 之后直接进入 `HUMAN_IMPLEMENTATION_REQUIRED`，且没有发生 design 角色调用。

## 本计划作出的决定（已评审，决定 2、4 见上方修订）

1. **合同形状与指纹。** 沿用变更聚合与 `product.nature="base"`，增加必填 `base={"scope": ..., "paths": [...], "must_stay_green": [...]}`；`goal` 仍在 product 顶层，`stories=[]`，其余旧字段保留原默认结构。`validate_product` 对 base 走单独的严格分支，禁止故事、验收条件和 product 共创输出；`approve_change` 按类型跳过“至少一个故事”，仍由人批准。`contract_digest` 保持现有规范化 JSON 算法，对包含 base 块的新合同自然计入指纹；不改变旧合同的字节输入或摘要。理由：保留现有状态、批准及报告外壳，又让 base 没有虚构的用户故事。
2. **必须保持绿。** 合同值固定为 `full_regression`、`system_smoke`、`build` 三项且不可删除或换成自选命令。项目 profile 新增 `base_full_commands` 与 `base_build_commands`，批准时解析并在 approval 内冻结命令摘要；两者均须非空，缺失则拒绝批准并提示配置。full 命令必须是项目维护者配置的完整回归入口，不能从某一已有 unit 命令臆测；系统冒烟无已安装套件也不能假称通过。候选验证还执行已配置的 unit/integration/checks，各已配置层不得跳过。理由：合同表达结果，命令由可信项目配置提供，明确区分完整回归与构建。
3. **G1 证据。** 新建 `.storyloop/evidence/<BASE-ID>/base-old-green.json`，记录批准合同摘要、`contract_commit`、旧 `baseline.source_head`、旧底座版本、三类命令与套件摘要、每条命令的退出码/测试数/耗时和输入树指纹。可信运行器在旧提交树的隔离副本执行，只有所有必需项确实执行并通过才写证据。`guard_g1` 按批准的 nature 分派：base 校验该文件及绑定的提交/指纹，其他类型原 RED 读取逻辑原样保留。用独立 `base_green_ready` 迁移事件进入 `IMPLEMENTING`，不伪造 RED 证据。若旧底座不绿，停点报告失败层和修复命令，不能开始实现。
4. **人工交互。** `base-propose` 先写 base 草案及旧格式提案关联，不碰源分支；批准后 `storyloop run --change <BASE-ID> --implementer human` 从锁定源头创建 `storyloop/<BASE-ID>` 分支，做 G1，停在现有 `DESIGN_APPROVAL_REQUIRED` 供人通过 `storyloop approve --change <BASE-ID> --design ...` 批准方案，之后停在新 `HUMAN_IMPLEMENTATION_REQUIRED`。人只在该分支提交合同列出的路径。`storyloop run --change <BASE-ID>` 恢复时比较锁定头、提交祖先及 `git diff --name-only -z <start_head>..HEAD` 的规范化路径集合，拒绝空提交、额外路径、漏路径、符号链接和控制面改动，报具体缺失/越界路径；不自动挑选或修改人的提交。合法候选才进入验证。若已有运行从停点重入，复核同一提交后不重复 G1 或提案。
5. **固定人工验收。** base 合同隐含一个稳定 ID `BASE-ACCEPT` 的整体人工条件，内容为“批准的目标与改动范围已在当前候选实现中满足”。沿用 `MANUAL_ACCEPTANCE_REQUIRED`、`storyloop accept --criterion BASE-ACCEPT --note ...` 及现有按候选指纹绑定的记录；报告明确列出合同路径和人的说明。候选提交变化后记录失效并重验。不按每个路径生成可被零散勾选的条件，避免漏掉跨文件影响。
6. **版本与回执。** 在 `FINALIZING` 中、合并与通用回执持久化之后推进 `baseline_version` 一个 patch。抽取 `base_upgrade` 现有候选摘要、回执 `ACCEPTING→ACCEPTED` 和崩溃恢复逻辑为共享推进操作，以 base 运行 ID 作幂等键，逐步落盘并校验旧/新 baseline 状态；重复 `run` 只恢复，不再加一。运行只能在回执 `ACCEPTED` 且 baseline 指向合并后的源头时进入 `PASSED`。旧回执读取规则保持原样，不重算历史摘要。理由：符合 I8 的断点恢复，避免先把底座升级再合并。
7. **调用方迁移。** `skills.install_skills`、`foundation_survey`、`lesson_landing`/`errata` 以及 `base_upgrade.propose_base_change` 统一调用“生成 base 草案”服务；保留原提案文件作关联和兼容读取。已写出的候选文件仍由人检查并在 base 分支提交，服务不得把它们提交到源分支。上游同步用 `scope=upstream`，CI 纳入用 `scope=ci`，技能包用 `scope=skills`，知识库与勘误用 `scope=knowledge`，普通集成点/底座文件用 `scope=foundation`。每项调用按现有路径和原因形成合同，不能借通用 scope 写其他区域。
8. **写权限。** `change_types.ChangeType.writable_scope` 只声明 base 可触达的类别（`foundation`、`integration`、`ci`、`upstream_mutable`、`skills`、`knowledge`）；实际允许集合取“类型权限 ∩ scope 权限 ∩ 批准合同精确路径”。CI 要原 `--allow-ci` 授权且 `scope=ci`；模块根内的上游同步要 `--allow-mutable` 且 `scope=upstream`。`project_boundaries` 按该集合分类，`run_guards.guard_g2` 再独立校验 Git 提交范围；非 base 的底座权限恒空，项目配置不能放宽。系统冒烟/判据路径在 E1 一律拒绝，直到 E2 注入 RED 门完成。只有 base 能修改底座路径或集成点。
9. **旧 PROPOSED 提案。** `base-update --proposal <ID>` 查到旧 `PROPOSED` 时，按旧 `changes`、`reason`、`baseline_source_head` 生成同 ID 的 base 草案（若已生成则核对关联摘要后复用），返回 `APPROVAL_REQUIRED` 与 `storyloop approve`/`run` 下一步；不执行旧的直接升级。已是 `ACCEPTING`/`ACCEPTED` 的历史提案走原回执恢复/只读结果，不创造第二个 base 变更。旧提案尚未有人工源分支提交时可继续；已有源分支提交的旧提案先要求人在新 base 分支重放提交，不自动重写源分支。理由：保住历史可读与恢复，不留骨架外新升级入口。
10. **T6 自举预留。** 运行记录与 G1/G2 证据显式记录引擎版本、引擎来源和目标树指纹；底座推进逻辑不能从目标仓库动态导入引擎源码。E1 实现不接入本仓库 `architecture.toml` 到 `init`，不实现固定 wheel 检测、发布门或 docs 类型，它们仍属 T6。E1 的端到端样本先用普通目标仓库；自举目标仓库要等 T6 的独立旧引擎判定就绪。

**交付边界说明：** 设计 §4.2 最终要求代理默认实现、跨厂商审查，以及判据变动时注入违规先红。E1 用明确的人工通道交付完整生命周期，不开放判据路径；这三项不能标成已实现，E2 以相同的 base 合同与状态机补齐。E3 才将 `BASE_CHANGE_REQUIRED` 自动衔接和 I13 标为 guarded。

## Task 1：base 合同、草案与批准

**测试先红：** 在 `tests/test_base_contract.py` 以初始化仓库生成 `BASE-*` 草案，断言 `nature=base`、`stories=[]`、目标/精确路径/scope/固定绿条件、批准后指纹锁定；空路径、重复/危险路径、scope 越权、无构建配置、伪造故事均拒绝；旧 feature/fix/refactor 指纹金样不变。先运行 `python -m unittest tests.test_base_contract -v`，预期因 base 类型/校验缺失失败。

**实现：** 在类型表加 `base` 与 `BASE` 前缀；单独校验 base 块，保留旧 product 版本；`base-propose` 产出变更草案与提案关联，`approve` 接受无故事的 base 并锁定合同与命令摘要。严格校验路径安全、scope 和旧底座头；旧产品角色 schema 不让代理生成 base 草案。运行 `python -m unittest tests.test_base_contract tests.test_change_types tests.test_change_approval tests.test_execution_profile tests.test_architecture -q`，预期全绿、零豁免。提交 `feat(base): 建立底座变更合同与批准入口`。

## Task 2：旧底座绿证据与 base G1

**测试先红：** `tests/test_base_lifecycle.py` 覆盖旧提交树三类检查绿才可进入实现，缺构建/未运行/跳过/退出码非零/证据换合同或提交/旧源头移动均被 G1 拒绝；普通类型仍要求原 RED。故意提供 RED 假证据不能替代 base 绿证据。运行 `python -m unittest tests.test_base_lifecycle -v`，预期缺少 base 绿分支而失败。

**实现：** 用隔离提交树运行器执行 `base_full_commands`、系统冒烟及 `base_build_commands`，写 `base-old-green.json`；在 `run_guards.guard_g1` 按批准类型校验，`run_transitions` 加 `base_green_ready`，必要时扩展 G1 context 传入批准合同但不能信任调用方自报。不可运行时给出精确停点，不生成成功证据。运行 `python -m unittest tests.test_base_lifecycle tests.test_run_transitions tests.test_project_loop_resume tests.test_architecture -q`，预期全绿。提交 `feat(base): 以旧底座全绿证据守护实现入口`。

## Task 3：人工分支、方案停点与路径权限

**测试先红：** 在 `tests/test_base_lifecycle.py` 覆盖批准后建独立分支、最重档位、方案经人批准、`HUMAN_IMPLEMENTATION_REQUIRED` 可显示/恢复；人在源分支提交、空提交、额外/漏改路径、CI 未授权、符号链接、控制面变动均被拒绝且不改状态；正常人工提交可继续。`tests/test_change_types.py` 与边界测试注入非 base 写底座、scope 错用、配置试图放宽，必须先红。运行目标模块，预期旧路径审计和停点不支持而失败。

**实现：** `project_loop`/`run_attempts` 分派人工实现路径，所有状态经 `run_transitions`；`project_boundaries` 以批准合同的精确路径与 scope 审计 Git 已提交范围，G2 复核。E1 拒绝系统冒烟及其他判据路径，既有 `BASE_CHANGE_REQUIRED` 对非 base 保持原行为。先运行 `python -m unittest tests.test_base_lifecycle tests.test_change_types tests.test_base_propose tests.test_project_loop_tampering -q`，预期新停点/越权断言失败；再运行同一命令加 `tests.test_architecture`，预期全绿、零豁免。提交 `feat(base): 增加人工实现停点与范围审计`。

## Task 4：验证、G2、人工验收与本地合并

**测试先红：** 在 `tests/test_base_lifecycle.py` 覆盖候选分支全量回归、系统冒烟、构建任一失败不得 VERIFIED；绑定候选提交，改动后旧证据/人工验收失效；独立人审失败不得过 G2；固定 `BASE-ACCEPT` 未确认不得报告或合并；确认后报告列出真实人工审查及路径，提交仍独立，G3 保留分支/提交检查。运行目标模块，预期 base 候选仍被原 acceptance RED/报告流程拒绝。
