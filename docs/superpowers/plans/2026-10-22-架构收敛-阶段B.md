## 本计划的具体选择（批准本计划时一并确认）

1. **覆盖全部现有写入点。** 设计 §10.1 的九个模块之外，还包括 `cost_resume`、`consistency`、`design_approval`、`routing_upgrade`。13 个模块共有 22 处直接修改/重建运行顶层 status 的语法位置，另有 `_new_run_state` 一处初始构造。嵌套判据、分流子状态、返回视图不算运行迁移；完整清单见[审计表](2026-10-22-架构收敛-阶段B-状态审计.md)。
2. **新增内核层，而不改既有归属。** 新增 `architecture.lifecycle_kernel`，title 为“变更生命周期内核”、rank=3；`run_transitions`、`run_guards` 归此组且为 base。原 lifecycle rank=6 继续承载上层编排。现有模块的 module/zone 不变；完成拆分后只删除 `project_loop`、`project_loop_finish` 的 `split="B"`。这是将已批准的生命周期职责拆成可调用内核和调度两部分，避免业务 rank=5 反向导入 rank=6。
3. **停点视图移出证据内核。** `pause`/`pause_for_boundary` 移到 reporting/mutable 的 `run_stops`；`next_steps` 的函数实现原样搬到 reporting/mutable 的 `run_hints`，原命令层模块只重新导出。内部 Python 导入点随搬迁更新，CLI 与输出不变。不在原 base 模块重新导出 mutable 函数。
4. **迁移与持久化分开，但顺序不变。** `transition` 统一修改 status；调用方保留原来的 save/checkpoint 顺序。对需要先检查、再执行 Git 的迁移，内核先运行固定守卫，再调用交付 effect，成功才写状态。不能在合并后才检查 G3，也不能先写 MERGED 再合并。
5. **按既有事实迁移，不借机补强。** G1/G2/G3 集中现有检查；缓存 RED 的弱校验、reset 的历史兼容分支等单列缺口。阶段 B 不新增必填持久字段，不把普通命令层标成具有不存在的逐层持久指纹。I12 的迁移集中与跳层拦截在 B 交付；读取声明式类型定义表在 C 交付。

不采用“所有业务导入现有 project_loop”方案，因为会新增向上依赖；不采用“把现有编排整体改成 base”方案，因为会把代理与阶段实现带入底座并改变已批准归属。

新接口如下，均为引擎内部接口；不写入状态格式：

```python
def transition(project: Path, state: dict, target: str, *, event: str,
               change: dict | None = None, context: dict | None = None,
               updates: dict | None = None,
               effect: Callable[[], dict] | None = None) -> dict: ...
def guard_g1(project: Path, state: dict, context: dict) -> None: ...
def guard_g2(project: Path, change: dict, state: dict, context: dict) -> None: ...
def guard_g3(project: Path, state: dict, context: dict) -> None: ...
def set_change_status(project: Path, change: dict, status: str) -> None: ...
```

`transition` 先查 `(event, source, target)`，再执行对应固定守卫，再执行可选 effect；最后将 effect 结果与 updates 合入 state，并只在这一处赋 status，返回 effect 结果。守卫失败不改 state、不执行 effect；effect 失败不推进 status，但不回滚已发生的 Git 副作用，沿用原崩溃恢复。updates/effect 结果不得夹带 status。禁止 `skip_guard`、`force`、`g2_passed=True` 或调用方自选 guard callback。

运行事件与变更聚合事件使用不相交的名称。`set_change_status` 对 change 建副本，分别以 `change_passed` / `change_superseded` 进入同一 transition 后按原2,000,000字节限制保存；这两个事件不套运行 G1–G3。仅两个生命周期写入调用它，保留旧批准/身份检查与幂等重试；不能将它做成绕过运行迁移的通用 setter。

effect 只封装原来的交付动作，例如：

```python
transition(project, state, "MERGED", event="merge", effect=lambda: {
    "merge_commit": finish_feature(project, state["feature_branch"],
                                   state["source_branch"])["merge_commit"]})
save_run(project, state)
```

G3 从旧 `_verify_verified_state` 原样抽取，先核验干净树、功能分支/报告提交、源分支和已验证产物；之后才能调用上面的 effect。已经合并但尚未落盘的恢复另用 `recover_merge`，原 `recover_completed_merge` 核验不能丢。
