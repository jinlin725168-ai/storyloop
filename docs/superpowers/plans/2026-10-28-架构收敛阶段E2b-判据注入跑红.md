# StoryLoop 架构收敛阶段 E2b：判据注入跑红实施计划

日期：2026-10-28；基线：`origin/main` `b9e01a3`。依据：[架构收敛设计 §4.2](../specs/2026-10-21-架构收敛-design.md)、E2a 计划末尾“E2b 预留”和两次真实试用。**本计划只交付一个可试用的端到端切片**：base 修改目标与判据，违规注入使新判据红，候选绿，经原通道审查、人工验收、合并并到 `PASSED`。

## 全局约束与本计划作出的决定

1. 保留旧 base 合同、指纹算法、提案、回执、状态文件与 `--implementer human`；新字段仅进入**新**合同的既有 `contract_digest`。不新增状态枚举或迁移边。E2a 代理仍需显式 `--implementer agent`；CI 路径、`.storyloop/**`、`acceptance/changes/**`、settings 和引擎证据内核仍不开放。
2. 新 base 提案可附一份**人提供**的 `--proof-file <JSON>`，`base-propose` 限大小读取并把内容冻结在提案与 `product.base.target_proof`；批准者核对后才 `approve`。字段固定为 `criterion_paths`（已批准的系统冒烟路径或声明的 `test_roots` 路径）、`check_ref`（`{"kind":"system_smoke","id":"coordinates"}` 或 `{"kind":"regression","layer":"unit"}`）、`violation_path`（同合同中一个已存在的普通目标文件）。第一批只支持一组证明、一个违规目标；不接受任意补丁、代理声明的探针或独立任意命令。理由：检查来自候选中持续执行的冒烟清单或已冻结的回归命令，违规来自 Git 源提交的真实旧值。
3. 新合同**修改判据路径时必须有** `target_proof`；未修改判据的用途在本批保持现状，仅走人工验收。判据路径必须在批准的精确路径集合内，且属于 `scope=foundation`；同一证明列出本次所有被改判据路径。人声明路径、检查引用和违规目标，引擎校验；代理只能实现批准路径，不能写证明声明或证据。`base-propose` 对声明的判据路径豁免现有 `test_roots` 可变区拒绝，`audit_base_scope` 与 `role_path_boundary` 仅对**有冻结证明的新合同**放开这些精确路径；未列入证明或其他 scope 仍拒绝。
4. G1 仍先在旧 `source_head` 上证明全量绿，**不要求新判据在旧代码上红**。候选提交后，引擎从该提交生成两份隔离副本：探针副本把 `violation_path` 换成 `source_head` 中该路径的 Git blob，正常副本不替换；两份都用候选的判据与同一 `check_ref` 命令。探针必须以普通测试失败退出，正常副本必须通过；超时、命令缺失或运行错误不算红。另照常跑完整回归、系统冒烟、构建、审查和人工验收。证据记录合同摘要、源提交及旧 blob OID、候选 commit/tree OID、判据路径的 blob OID、检查引用及实际 argv、两次退出结果；由引擎写文件并把文件 SHA 写进 state。G2 重查这些绑定，报告展示红/绿及目标；代理自报不算证据。代理可以知道旧值，但不能选取或改写引擎执行的 Git blob；本批不声称防住同用户恶意进程专门迎合探针。
5. 系统冒烟保护的旧摘要不能用于验证尚未合并的新清单：候选验证只读候选 Git 树的 manifest 与判据文件，在隔离副本运行；合并后复用 `adopt_system_smoke` 更新保护摘要，再沿 E1 的回执和底座版本幂等推进。只对本次获批准的 system-smoke 路径这样做，不能放松普通变更的保护检查。人工 `BASE-ACCEPT` 仍必经，确认目标与探针证据；自动红/绿是额外证据，不能替代人验收。
6. 恢复沿用 E1/E2a：合并前中断或失配整次作废重来，不采纳磁盘残留证明；源分支是否已合并按 Git 事实判定，合并后只续回执/版本。StoryLoop 不是沙箱；隔离副本和代理独立 worktree 沿用现有威胁模型，不加新的操作系统隔离。

## 新写入与中断点（先测再实现）

| 中断点 | 已保存状态 / Git 事实 | 期望与测试 |
|---|---|---|
| 证明文件写完、state 尚无 SHA | `IMPLEMENTING`，候选已提交，文件无可信绑定 | 走现有 `base_inflight`/`base_restart` 作废重来；`test_probe_write_before_state_restarts` |
| SHA 已保存、G2 前证明或候选变化 | `BASE_REVIEW_REQUIRED` 或验收停点，源未合并 | 既有前合并重来；`test_probe_tamper_or_candidate_change_restarts` |
| 已合并、冒烟保护摘要更新前后中断 | 源 ref 含报告提交，可能旧保护摘要 | 按 Git 事实续合并后路径，重复 `adopt_system_smoke` 与既有 finalization 后仍只加一版；`test_merged_smoke_adoption_is_idempotent` |

## 文件与任务（每项先测红，再实现、测绿、提交）

**文件结构：** `base_upgrade.py`/`product_contract.py`/`cli.py` 负责证明声明进入新提案和合同；`project_boundaries.py`、`base_agent_transfer.py` 负责精确路径授权；新 `base_criterion_probe.py` 只负责 Git blob 注入与隔离红/绿；`base_execution.py`、`run_guards.py`、`base_finalization.py` 连接证据、G2、冒烟保护；`docs/api.md` 写人操作。预计测试：`tests/test_base_criterion_contract.py`（FAST）、`tests/test_base_criterion_safety.py`（SAFETY，进 Windows platform）、`tests/test_base_criterion_flow.py`（END_TO_END）；按单模块实际耗时调整 `tests/suites.py`。

### Task 1：冻结目标证明与精确权限

- [ ] 在合同测试写：旧合同指纹与读取不变；无证明的判据路径继续拒绝；有证明时仅批准的 `acceptance/smoke/**` 或声明 `test_roots` 下路径可进入 `scope=foundation`，`violation_path` 必须是源提交已有普通文件、在合同路径内，`check_ref` 只能指向系统冒烟 ID 或已配置回归层。先跑 `python -m unittest tests.test_base_criterion_contract tests.test_base_criterion_safety`，预期新增断言失败。
- [ ] 增量实现 `--proof-file` 导入、`target_proof` 校验/冻结、提案 SHA 绑定和路径授权；代理可写列表与搬回审计采用同一批准集合。测试转绿并跑 `tests.test_change_approval tests.test_project_boundaries tests.test_architecture`、`ruff check storyloop tests examples`；提交 `feat(base): 冻结判据目标证明与精确路径`。

### Task 2：候选隔离注入跑红并绑定证据

- [ ] 在安全/流程测试写：`pom.xml` 由旧坐标改新坐标，新冒烟检查在注入旧 blob 时红、正常候选绿；无新判据、假红（超时/缺命令）、红绿颠倒、源 blob/候选/证明文件失配均不能到审查；覆盖上表前两处中断。先跑 `python -m unittest tests.test_base_criterion_safety tests.test_base_criterion_flow`，确认失败。
- [ ] 复用 `run_commands_at_commit` 的安全检出/运行方式实现临时副本与注入；只从 Git 对象取输入，绝不改主工作区或代理树。候选证据保存 SHA，G2 对新合同必查，旧合同沿原守卫；报告增量附证明。测试转绿并跑 `tests.test_base_agent_flow tests.test_base_trust tests.test_architecture`、ruff；提交 `feat(base): 用源提交违规证明新判据先红`。

### Task 3：冒烟合并闭环与真实试用

- [ ] 先写上表合并后中断测试，以及候选新冒烟清单能运行、普通 feature 修改冒烟仍拒绝、合并后保护摘要与新清单一致、后续 `storyloop ci` 可跑的测试，确认失败。实现候选专用冒烟验证与合并后的幂等 `adopt_system_smoke`；复用 E1 `FINALIZING`、回执和版本推进，不加恢复分支。测试转绿，更新 `docs/api.md`，提交 `feat(base): 让新冒烟判据随底座合并生效`。
- [ ] 用临时真实项目试用：旧 `pom.xml` 坐标 `org.old:app:1.0`，base 提案批准 `pom.xml`、冒烟 manifest 与新 `check_coordinates.py`；证明指向冒烟 ID `coordinates`、违规目标 `pom.xml`。显式 `--implementer agent`（可用测试适配器）生成/批准方案，候选把坐标改成 `com.example:app:1.1`；探针换回旧 blob 后检查红，原候选检查绿，再跨厂商审查、人工验收、合并、回执，直到 `PASSED` 且底座版本只加一。实施 PR 附命令、关键输出及证据中的两个 Git OID。

## 验收与后续

单元/安全/流程测试和 PR CI 必过，`ruff` 与架构测试零豁免；以**上述真实试用到 `PASSED`** 为交付门槛。若实现触及 Windows 敏感的路径、符号链接或换行处理，再手动触发 Linux/Windows 完整 core 并等待结果；否则不额外要求。按实现时实际调用顺序核对三处中断点，发现新增写入窗口先补同类测试；不扩展为逐窗口精细恢复。

**后续：** 多违规目标/多证明、全新目标文件的合成违规、对 arbitrary 检查命令的开放、复杂崩溃窗口与超出既有威胁模型的加固。E2b 不做 E3 的 `blocked_by` 衔接，也不宣称 T6 固定旧引擎自举已完成。

**待人决定：** 是否让所有新 base 合同都强制声明目标检查？A：全部强制，覆盖更广但会阻断上游同步、知识/技能等难以自动断言的旧用途；B（推荐）：本批只在改判据路径时强制，其他 base 维持人工验收，非判据路径的目标证明留待试用后扩展。推荐 B 以先完成可验证的真实切片，再决定是否扩大强制范围。
