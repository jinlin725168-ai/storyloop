# StoryLoop 架构收敛阶段 C 实施计划

> **执行要求：** 使用 `executing-plans` 按任务逐项实施。每项先写测试并确认失败，再实现并确认通过；每项单独提交。

**目标：** 集中 feature、fix、refactor 的既有策略到一个底座 Python 声明式类型定义表，并使判据、分流、边界审计和生命周期守卫读取该定义表，同时保持既有行为。

**架构：** 新建 `storyloop/change_types.py`，以只读声明常量承载每类的判据底线、可写范围、必经阶段、最低档位和人审要求，并提供类型查询。逐步迁移当前硬编码策略；用测试假类型证明相同骨架无需生产代码特判即可扩展。base 专属入口、权限和策略仍留在阶段 E。

**技术栈：** Python 标准库、pytest、现有 StoryLoop 模块及架构声明。

**设计：** `docs/superpowers/specs/2026-10-21-架构收敛-design.md`，重点 §4.2、§4.3、§5.1、§7、§10.1、§14.1、§15。

## 全局约束

- 只迁移 feature、fix、refactor，三类行为、持久格式、CLI 与输出保持不变。
- 类型定义采用底座 Python 模块中的声明式常量，不改用外部 TOML。
- 阶段 A–D 的“底座”只用于静态架构声明，不接入用户仓库 `baseline.json` 或运行时边界审计。
- 不实现 base 类型、阶段 D 剩余拆分、阶段 E、T6 或执行画像；不新增豁免，不修改已批准归属或测试预期。
- 在隔离 worktree `refactor/architecture-stage-c` 操作，不在共享目录切换分支。
- 每任务单独提交；作者身份 `jinlin725168-ai`，无 Co-Authored-By；中文提交格式 `<type>(<scope>): <subject>`。

## 现状与文件职责

- `models.py`：产品结构校验、类型枚举与类型取值。
- `changes.py`：变更 ID 类型前缀。
- `requirement_checklist.py`：分类型判据底线。
- `project_loop_gates.py`：特征化要求、锁路径检查与阶段门。
- `planning.py`：重档/refactor 锁路径策略。
- `routing_policy.py`、`routing_state.py`、`intake.py`：类型合法性、路由信号和档位策略。
- `project_boundaries.py`、`run_guards.py`、必要时 `run_transitions.py`：可写范围与生命周期守卫。
- `architecture.toml`：模块归属和 I12 登记。

开始迁移前逐项对照设计 §4.2 和上述现状。无法从批准设计与当前实现无歧义确定的规则，先停止并提交问题供评审，不自行制定策略。

## Task 1：定义类型策略及查询接口

**文件：** 新建 `storyloop/change_types.py`、`tests/test_change_types.py`；修改 `storyloop/models.py`。

**接口：** `CHANGE_TYPES` 只读映射，键为现有三类；每项提供 `criteria_floor`、`writable_scope`、`required_stages`、`minimum_tier`、`human_review`。`type_of(product)` 保持缺省 `feature`；`definition_for(type_name)` 对未知类型以现有安全错误拒绝。

- [ ] 测试三类完整定义、默认 feature、未知类型拒绝、调用方不能修改定义。
- [ ] 先运行新测试，确认缺失接口时失败。
- [ ] 按设计表及当前代码登记三类现有策略；保持 `models.NATURES` 兼容，并从定义表导出合法类型集合。
- [ ] 运行该测试与模型校验相关测试，确认通过。
- [ ] 提交 `feat(architecture): 声明变更类型策略表`。
