# 需求共创技能 第 2 批：三层定制、定制视图与试用修正 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 项目可以用团队定制文件和个人定制文件调整 spec-craft，升级技能不会冲掉定制；引擎能确定性地生成"技能本体 + 定制"的视图和摘要；同时修正第 1 批试用暴露的三个内容问题。

**Architecture:** 定制文件放在仓库根目录 `storyloop-custom/`：团队文件进 Git，个人文件不进 Git。新模块 `storyloop/skill_custom.py` 负责读取、校验、按固定规则合并定制，并把合并结果渲染进视图。CLI `storyloop skills <项目> --view <技能名>` 把视图写到控制面 `.storyloop/skills-view/<技能名>.md`，并输出摘要。安装到 `.claude/skills/` 的仍是技能本体原样，不随定制变化。`storyloop-custom/` 仿照 `openspec/lessons/` 的做法：不计入底座指纹，代理写入算越界。

**Tech Stack:** Python 3.11 标准库（`tomllib`、`hashlib`）；`unittest`；Markdown。

**Spec:** `docs/superpowers/specs/2026-10-23-需求共创技能-design.md`（§9.1–§9.3、§13 第 2 批、§13.1 第 5 条）；第 1 批试用记录 `docs/validation/2026-10-24-spec-craft-第1批试用.md` 的"本次发现的问题"第 2–4 条。

## Global Constraints

- 合并规则（设计 §9.2）：标量以后者为准；普通数组追加；带 `code` 键的表数组，键相同就替换，键不同就追加。合并顺序：团队文件 → 个人文件。
- 不能定制的内容（设计 §9.2）：输出格式、引擎约束、"只能由人判断的事"。定制只能**追加**覆盖地图分类和模板节，不能删除或改写内置内容。
- 团队定制 `storyloop-custom/spec-craft.toml`，进 Git；个人定制 `storyloop-custom/spec-craft.user.toml`，不进 Git，由引擎写进 `.git/info/exclude`（设计 §9.2）。
- spec-craft 仍然不下发给任何引擎角色，frontmatter 仍然只有 `name`、`version`、`description`（第 1 批约束不变，设计 §9.4）。
- 打包只含 `skills/**/*.md`，技能包里不加 CSV 或 TOML 文件。
- 不引入第三方依赖；单个文件不超过 500 行。
- 每次提交前 `ruff check storyloop tests examples` 必须通过。
- 新的测试模块：涉及路径保护、越权写入的放进 `tests/suites.py` 的 `SAFETY` 组，让 Windows 上的 PR 检查也能覆盖；其余按耗时放进 `FAST` 或 `END_TO_END`。
- `tests/test_architecture.py` 保持零豁免；新模块要在 `storyloop/architecture.toml` 登记。
- commit 格式 `<type>(<scope>): <subject>`，中文；只用仓库用户身份，不加 Co-Authored-By trailer。

## 本计划作出的决定（实现前请评审）

1. **定制视图写在控制面，不装进 `.claude/skills/`。** 设计 §9.2 写的是"`storyloop skills` 安装时写入合并视图"。但已初始化项目上，`.claude/skills/` 属于底座，每次改定制都重装，就要走一次底座变更，"人可以直接改定制"就落空了。所以安装的仍是技能本体；`SKILL.md` 开头写明"项目里有定制文件时，先运行 `storyloop skills <项目> --view spec-craft`，按输出的项目定制执行"。
2. **`storyloop-custom/` 仿照 `openspec/lessons/` 处理**：从底座指纹中排除（`baseline._foundation_paths`），代理写入归类为越界（`project_boundaries` 新类别 `CUSTOM_PROTECTED`，并加入 `forbidden_paths`）。人可以直接编辑、提交，不触发底座漂移。
3. **技能包里不放 `customize.toml` 和 `coverage.csv`**：打包只含 `.md`；内置的覆盖地图仍是 `references/clarify.md` 里的表格，定制只追加新行。没有定制文件时，视图与 `skills.skill_text(project, "spec-craft")` 完全相同。
4. **第 1 批试用问题的修正方式**：
   - **正例、反例重新定义，按"前提是否成立"划分**：
     - 正例：规则的前提成立时，系统按规则做（对 IF…THEN 规则，就是异常情况发生、系统作出应对）；
     - 反例：前提不成立，或处在规则边界之外时，系统不应按这条规则做，即不误触发。
     - 行类型的默认值：正例通常是实现前应失败的行（positive、degradation、unknown_state）；反例通常是实现前应通过的行（regression、non_goal）。但最终以"在旧代码上会不会失败"为准，必须给出判断和一句理由，不再允许写"待定"。
   - **被推翻的说法**：需求文档的各节只保留当前有效的内容；原说法只出现在"澄清记录"里，写成"原说法 → 新说法"。评估块也遵守这一条。
   - **所有假设都写进"假设"表**：最终回复不得列出表外的新假设，发现新假设就先写进表里。
5. **spec-craft 版本升到 1.1.0**：改了流程（新增定制一步）和例子的定义。
6. **设计文档同步**：§6.2 的正反定义改成上面第 4 条的说法；§9.2 补一句"视图写在控制面，安装的仍是技能本体"。

## Review Focus

1. 定制文件里出现未知的键（拼写错误，或者试图改"只能由人判断的事"），必须报错并点名这个键，不能静默忽略。→ Task 1 `test_unknown_keys_are_rejected_by_name`。
2. 个人定制文件被误提交进 Git：引擎要写好 `.git/info/exclude`，并且在视图里提示"个人定制已被 Git 跟踪"。→ Task 3 `test_tracked_user_file_is_reported`。
3. 定制里的 `glossary` 路径指向仓库外，或者是符号链接，必须拒绝。→ Task 1 `test_glossary_must_be_a_safe_repository_path`。
4. 定制文件不是合法的 TOML，或者不是 UTF-8：报错要说明是哪个文件、第几行，不能抛出原始异常。→ Task 1 `test_invalid_toml_names_the_file`。
5. 已初始化的项目上，人修改并提交 `storyloop-custom/spec-craft.toml` 之后，`storyloop run` 不会报底座漂移。→ Task 3 `test_committing_team_customization_does_not_drift_the_base`。

### Task 1: 读取、校验与合并定制

**Files:**
- Create: `storyloop/skill_custom.py`
- Modify: `storyloop/architecture.toml`
- Test: `tests/test_skill_custom.py`

**Interfaces:**
- Produces:

```python
CUSTOM_ROOT = "storyloop-custom"
CUSTOMIZABLE = {"spec-craft"}                      # 只有登记过的技能可以定制
def custom_paths(project: Path, name: str) -> tuple[Path, Path]   # (团队文件, 个人文件)
def load_customization(project: Path, name: str) -> dict
```

`load_customization` 的返回值固定为

```python
{"version": 1, "preferences": [str, ...], "glossary": str | None,
 "coverage": [{"code", "name", "check"}, ...], "sections": [{"code", "document", "title", "guidance"}, ...],
 "sources": [{"path": str, "sha256": str}, ...]}   # 实际读到的文件，按合并顺序
```

文件不存在就跳过；两个都不存在时，各列表为空，`glossary` 为 `None`，`sources` 为空。

**校验规则**：
- 顶层键只能是 `version`、`preferences`、`glossary`、`coverage`、`sections`；`version` 必须为 `1`；
- `preferences` 是字符串数组；
- `glossary` 是仓库内的相对路径，用 `path_security.safe_target` 校验，不能是符号链接；
- `coverage` 每项必须恰好有 `code`、`name`、`check` 三个非空字符串；
- `sections` 每项必须恰好有 `code`、`document`（`requirement` 或 `spec`）、`title`、`guidance`；
- `code` 只能由小写字母、数字、连字符组成。

违规时抛 `StoryLoopError`，消息里带文件的相对路径和出错的键。TOML 解析错误也要带上文件路径和行号（取自 `tomllib.TOMLDecodeError`）。
