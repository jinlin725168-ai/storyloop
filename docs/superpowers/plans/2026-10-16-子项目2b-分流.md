> **For agentic workers:** REQUIRED SUB-SKILL: Use subagent-driven-development (recommended) or executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Architecture:** 引擎依据带来源的证据执行确定性规则，角色只提供结构化判断。入口证据与 run 分开保存；规划状态与实现失败计数分开；沿用受保护判据、只读调用和恢复机制。

**Tech Stack:** Python 标准库、unittest、Git、现有 JSON 文件状态和 Codex/Claude 适配器；不新增第三方依赖。

**Spec:** [已批准的 2b 设计](../specs/2026-10-16-子项目2b-分流-design.md)，2026-10-16 用户“按草案进入详细实施计划”批准推荐方案。

## Global Constraints

- `light < standard < heavy`。拆分是 heavy 之上的停点，不是第四种执行档位。
- 旧的已批准合同、已有运行及其续跑保持 legacy 路径，不重算摘要、不补扣预算、不在恢复中突然插入审批。
- 已配置但失败的检查不可豁免；缺少 checks/system smoke 允许绑定摘要、附理由的人工缺口确认，不标成 PASSED。
- 所有档位保留 RED、基线计数、零执行检查、重检查收尾、人工验收、安全边界及审查。
- L3 只升不降；规划不消耗实现轮次，不重置已用预算，不扩大写权限。
- 无数据库 schema 修改、核心依赖升级或主分支提交。已批准的 CLI/角色协议扩展在本计划范围内。
- 新增/修改函数不超过 50 行；新增文件不超过 500 行；现有接近上限的模块先按责任提取。
- 不访问生产库、凭证或业务数据；测试使用本地临时仓库；图例使用 Mermaid。

## 跨任务数据与接口约定

### 1. Signals、规则及 Decision（任务 1–2）

`Signals` 是 JSON dict，固定字段如下；数字未知为 null，布尔事实使用 `yes/no/unknown`，禁止用缺失等价 no。

```python
signals = {
    "nature": "feature", "stories": 1, "criteria": 4, "manual": 0,
    "existing_files": 1, "created_files": 0, "interfaces": 0,
    "max_references": 0, "complete": True,
    "risks": {key: "no" for key in (
        "sensitive", "migration", "external_contract", "new_interface",
        "crosscut", "principle_deviation", "hard_verify_high_cost",
        "dependency_swap", "persistent_state", "human_choice", "guard")},
}
```

证据单独保存：`{field, value, source, locations, commit}`；source 限 `engine/role/human`。规模由引擎复核后覆盖角色估计；风险 yes 合并不可被后续 no 抹掉。`complete` 由引擎根据范围/证据覆盖生成，角色不能自己宣布完整。

`routing` 配置：`policy_version=1`，`split_stories=6`，`split_files=15`，`split_interfaces=8`，`heavy_stories=4`，`heavy_existing=8`，`heavy_references=30`，`manual_ratio=0.25`，`sensitive_paths=[]`，`guard_paths=[]`。拒绝未知键、bool 冒充整数、非有限数字、非正阈值、heavy_stories > split_stories、heavy_existing > split_files、比例不在 [0,1]、危险路径。

`Decision`：`{tier, split, reasons, unresolved}`。reasons 元素 `{rule_id, fields, values}`；unresolved 是字段路径列表，非自由文本控制指令。`evaluate` 每次从 Signals 重算 GUARD，再与已保存档位取 max，不对旧档位重复 GUARD。

### 2. Intake 与就绪记录（任务 3–4）

`product.assessment` 可选；新协议语义上必需。结构：`verifiable_goal: bool`，`scope: {touched: list[str], creates: list[str], interfaces: list[str], symbols: list[dict]}`，`risks: dict[str, {value, evidence}]`，`criteria: list[{story_id, criterion_id, feasibility, method, existence, evidence}]`。feasibility 限 `local_automated/manual/infeasible/unknown`；existence 限 `exists/partial/absent/unknown`；evidence 含位置或明确的搜索范围，不接受仅一句“没有”。每条条件恰好一条记录，引用绑定 source_commit。

`intake`：`{version, product_digest, source_commit, policy_digest, assessment_digest, decision, status, evidence}`。digest 均用 canonical JSON（sort_keys、紧凑 separators、UTF-8、allow_nan=False）SHA-256。批准绑定此记录；不要把引擎生成的 intake 塞回 product 引发摘要自引用。

就绪记录 `.storyloop/state/readiness.json`：`{version, binding, digest, layers, gaps, blockers, status, approval}`；binding 为 `{baseline_version, source_commit, test_config_digest, suite_digests}`。测试层记录 discovered/executed/failed/skipped（未知 null）、命令指纹及证据文件位置。输出截断不得丢失最终计数，超限解析失败按未知处理。

状态：`READY` / `PROJECT_NOT_READY` / `READINESS_APPROVAL_REQUIRED`。READY 可带已确认 gaps，但对应层仍 `MISSING`。checks 是静态检查，按命令成功判定，不要求解析“测试数”；unit/integration/system smoke 才受零执行及未知执行数门禁。无自动测试层至少一次实际执行 >0 则不能 READY。

### 3. Run routing、Plan 与审批（任务 5–9）

新草案 `routing_version=1`；旧状态没有此字段。新 run 的 routing：`{version, initial_tier, effective_tier, policy, policy_digest, reasons, history, scope, budget_source, limit}`。history 每项 `{stage, attempt, from_tier, to_tier, assessment_digest, reason}`；同一摘要重入不重复追加。

`Plan`：`{version, id, binding, main_option, options, questions, design, status}`。options 每项 `{id, summary, touched, creates, interfaces, risks, forbidden_paths, constraints, regression, migration, dependencies, principle_checks}`；1 个主方案和最多 2 个真实备选，不凑数。binding 含 product_digest/source_commit/scope_digest/suite_digest/policy_digest；L3 再含 candidate_digest。plan.id 是除 id/approval/status 外内容的摘要；批准选项与 plan.id 同时绑定。

新停止状态：入口的 `EXPLORATION_RECOMMENDED/ORACLE_INFEASIBLE/NEEDS_INPUT` 不创建 run；规划的 `DESIGN_APPROVAL_REQUIRED/DESIGN_REVISION_REQUIRED/SPLIT_RECOMMENDED` 保存 run。`NEEDS_SPEC_FIX/ORACLE_DEFECT/NEEDS_INPUT` 继续复用现有语义并记录 planning 阶段。

`approve --design PLAN_ID` 默认选 main_option；多方案选择使用 `--option OPTION_ID`（本计划将草案“选择具体方案”落实为显式参数）。无 --option 时不可猜测另一个选项。`approve --continue-heavy ASSESSMENT_ID --reason TEXT` 只解除对应拆分停点，不能充当方案批准。

配置显式 max_attempts 优先。不存在该键时，新协议缺省 light=2/standard=3/heavy=4；legacy 仍 3。升级只增默认限额；显式调高限额可恢复，调低不退还轮次。依旧使用已有实现调用计数和 AGENT_UNAVAILABLE 归还规则。
