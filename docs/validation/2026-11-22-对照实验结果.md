# 对照实验结果：StoryLoop 对比直接用 Claude Code

方案见 `docs/plans/2026-11-22-对照实验方案.md`。本文记录 12 次有效运行（6 个样本，每组各 1 次）和 C 组在两个分歧样本上的 2 次重跑的结果、按方案决策表得出的结论，以及这些结论有哪些不足。

## 设置

- 引擎：`cab0220`；模型：两组都用 opus；单次墙钟上限 2 小时。
- S 组：sqlite-utils 的 3 个样本按快速上手文档运行（`change --idea` → 冻结的人的答案 → `approve`）；bench 的 3 个 Case 用 `bench run --attempts-per-side 1` 运行。
- C 组：一次 `claude -p`，工具白名单与 S 组的代理相同（另加 `git add`/`git commit`），`--max-turns 200`，不能提问。
- 两组都在由 `git archive` 生成的单提交新仓库里运行，看不到上游历史和 Gold。运行结束后再在独立副本上判定 Gold。
- 提示内容的差别：bench Case 的 C 组提示带有 Case 已批准合同的全部规则和验收条件；sqlite-utils 的 C 组提示只有冻结的需求文字。所以对 bench 三例来说，C 组实际相当于方案里的 C2 组（拿到合同的 Claude Code）。

### 关键的一例：dogfood6 的 C 组

Gold 中失败的检查是 AC-6 `test_ac6_a_stop_saved_before_the_fix_shows_the_findings`：修复之前已保存、停点里没有意见列表的 DESIGN_REVISION_REQUIRED 停点，应当从运行状态里保存的审查结果显示阻塞意见。C 组的实现对这类停点什么也不显示。

AC-6 和对应的规则都原样写在 C 组的提示里。C 组没有漏看需求，问题出在它没有完成验证：它把全量测试放到后台运行，然后结束了会话，结束时说"跑完会自动通知我，届时我检查结果并提交"。在 `claude -p` 模式下不会有后续通知，所以留下的是一份未提交、也未验证的改动。

S 组在同一例中由外环验证跑过了全部验收条件，结果是 PASSED，Gold 也通过。

这正是方案里定义为"最关键"的指标：**自报完成但错误**。首轮中 S 组 0 次，C 组 1 次。不过这一例的 C 组说法是"测试还在跑"，而不是"已完成"。在交互式使用中，人看到这句话会等它跑完；只有在无人值守时，它才会被当作完成而交付。重跑结果显示这次失败不是必然的，见下文。

### dogfood3 的 S 组停点

S 组在 heavy 档先后经过 replan 和 acceptance_repair，最后停在 ORACLE_DEFECT，花了 $49.58，没有交付。C 组用 $1.41 交付了能通过 Gold 的改动，尽管它结束时同样说"等待完整测试结束"，改动也没有提交。这一例中 S 组没有做错，诚实地停了下来，但成本高，也没有交付。

## 分歧样本的重跑（C 组）

按方案"有分歧的样本再加跑 1 次"，C 组在 dogfood6 和 dogfood3 上用同样的提示和设置各重跑了 1 次。S 组按人的决定不重跑。

| 样本 | Gold | 结束时的说法 | 费用 | 墙钟 |
|---|---|---|---|---|
| dogfood6 重跑 | ✅ | 已完成，全量 1722 个测试通过，已提交 | $1.45 | 19 分钟 |
| dogfood3 重跑 | ✅ | 已完成，已提交。全量测试分 20 片并行跑，剩 1 个与改动无关的收集错误，已说明 | $2.17 | 76 分钟 |

两次重跑都没有再出现"后台跑测试后结束会话"的情况，都做了完整验证并提交。所以首轮 dogfood6 的失败属于偶发：8 次 C 组运行中出现 1 次。

## 按方案决策表

| 决策表条件 | 是否满足 |
|---|---|
| S 正确数明显多于 C | 否。S 交付 5 例且全部正确，1 例停下；C 交付 8 次，其中 7 次正确 |
| C 有"自报完成但错误"而 S 没有 | 首轮有 1 例（dogfood6），重跑中没有再出现；而且那一例的说法是"测试还在跑"，不是"已完成" |
| 两组正确数接近，S 贵很多 | 是。S 有效运行 $137.08；C 首轮 $4.42，S 约为 C 的 31 倍。在 sqlite-utils 小改动上，S 的墙钟约为 C 的 10 倍 |

结论落在第二行，并且接近第三行，即"C 不差于 S"：

1. **小而清楚的改动**（sqlite-utils 三例）：C 组用 3%～8% 的费用、约十分之一的时间交出了同样正确的结果。在这类改动上，StoryLoop 的各道门在本实验中没有带来可测量的质量收益。
2. **自身仓库、测试慢、涉及已保存状态的改动**（dogfood 三例）：S 组唯一的质量收益是防住了 1 次偶发的未验证交付。这依靠的是独立的外环验证，也就是不信任代理的自报、把验收条件全部实际跑完。合同本身不是差别所在，因为 C 组也拿到了合同。另一方面，S 组在 dogfood3 上花 $49.58 停了下来，而 C 组两次都交付了正确结果。

## 对下一步的含义（待复盘确认）

- **在小改动上，S 不比 C 好，而且贵得多。** 降本时可以把 C 组的量级当作目标：light 档只保留实现和独立的验收验证。
- **外环验证是唯一观察到的质量来源。** 它也最便宜：不需要额外的模型调用，只需要实际运行验收检查。
- **定位需要重新审视。** 按方案第三行，应暂停扩展功能。StoryLoop 的价值可能只在"无人值守，必须拒绝未经验证的完成"或更大、更高风险的改动上，这需要另设实验来验证。
- **dogfood3 的 S 停点值得单独排查。** C 组能用 $1～2 做对的需求，S 组却经过 replan 和 acceptance_repair 后停在 ORACLE_DEFECT，说明 heavy 档的流程可能在制造障碍，而不是在消除风险。

## 局限

- 每组每样本只有 1 次，C 组在 2 个样本上多跑了 1 次，结论只能当作方向信号。
- C 组首轮的失败与 `claude -p` 的一个特性有关：代理把命令放到后台后结束会话，就不会再收到通知。交互式的 Claude Code 不会这样结束。
- bench 三例的需求来自 StoryLoop 自身仓库，Case 的修订（v2.3）也是本项目自己做的。为降低偏向，两组用的是同一份 Gold，C 组还拿到了完整合同。
- S 组另有约 $42 花在因额度和网络中断而作废的运行上，未计入上表。

## 费用

有效运行 $145.12（S $137.08，C $8.04，含重跑），加上作废的运行约 $42，合计约 $187，在批准的 $120～210 以内。
