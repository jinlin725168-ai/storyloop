# H 验证：两个真实需求并行跑、按验证落地

日期：2026-11-18。对象：F/G 用过的 sqlite-utils 克隆。引擎为 H 分支，代理为 Claude Code。

## 过程

1. 依次起草两个相邻的需求，故意改同一个文件（`sqlite_utils/cli.py`、`docs/cli-reference.rst`）的不同段落：
   - A：`indexes --name`
   - B：`triggers --name`
2. 两份草案都按推荐项回答问题并确认假设。A 剩下的一个覆盖类阻断项由引擎自动退回修正。
3. `workers start` 两次，两个 worker 在各自的 clone 里同时跑完整闭环，项目工作区保持干净。
4. 13 分钟后两个都 `PASSED`：
   - A：11 次调用、$9.74；
   - B：9 次调用、$8.58。
   `inbox` 列出两条"待落地"。
5. `workers land A`：项目分支未动过，快进（`exact`，0.2 秒）。
6. `workers land B`：项目分支已含 A，在临时 clone 合并后复验 B 的验收、系统冒烟与单元层（`reverified`，19 秒），绿了才快进。

## 结果

- 项目 main 同时包含两个功能：上游 1556 个测试全绿，`cog --check` 通过，两条命令的 `--help` 都有 `--name`。
- `status` 总览显示 4 个变更全部完成，`workers status` 显示两个 worker 都已落地。
- 每个变更人工触达 3 次，全部是决定：回答问题、`workers start`、`workers land`。
- 两个需求串行要约 26 分钟，并行用了 13 分钟加 19 秒复验。

## 暴露的问题

1. 往 `config.json` 加 `github` 配置后，已批准的准备度缺口失效，两份新草案被拦。原因是准备度摘要覆盖了整份配置。现在排除与测试无关的键，没有这些键的配置摘要与以前相同。已修复。
2. `storyloop readiness` 遇到准备度缺口时报 `TypeError`。这是 F 的证据截断引入的回归：准备度停点的证据是字典，不能切片。已修复。
3. 复验落地的合并提交信息是 git 默认的 "Merge commit '…'"，现在写明变更 ID 与"复验后落地"。已修复。
4. 报告在 worker 里生成，而 worker 不带人工触达账，所以报告摘要没有"人工触达"一行；`log` 和 `metrics` 的计数正确。尚未修复。
