# 方案影响分析

从已批准合同的 `verification_entries` 出发，沿当前源码追到拟修改文件，再追至少一层直接调用方。每条链记录入口 ID、AC、实际 `path:line`、候选 `touched/creates` 和可观察变化；动态调用或找不到引用时标明未知，不填零。

1. 先核对合同与受保护 manifest 的入口和 AC，再读当前代码、配置、测试。方案中的 `entry_paths` 必须解释公共入口如何经过所列改动文件；无法证明就提出设计问题。
2. 比较输入、返回值、错误／停点状态、副作用和默认值；检查调用方、持久化数据、接口兼容、支持的环境与有效缓解。环境范围未知时列待验证项，不臆造版本。
3. 对每条会替换旧行为的 AC，先搜旧输出的字面量与归一化占位符，再沿测试读取的 fixture/snapshot 路径追到实际断言；核对 `test_roots` 下的 golden JSON、快照和调用这些文件的测试。不能只因测试名称或方案摘要说“不相关”就跳过。记录 `path:line`、旧值、合同新值和实际测试命令。
4. 把需更新的已有判据写入选定方案的 `regression_updates: [{path, criterion_ids, reason}]`，路径也列入 `touched`；只更新合同明确替换的断言，保留其他字段和回归强度。实现期新发现的冲突交回 replan，不由实现角色自行扩大范围。
5. 输出简表：`入口/AC → 调用链 → touched/creates → 消费者/兼容风险 → 受影响测试/快照 → 验证命令`。风险与证据确定性分开标注，未检查的路径如实列出。

本技能只帮助设计判断；StoryLoop 的方案范围、文件路径、风险证据与批准门禁由引擎校验，不能用影响分析放宽。

思路参考 HelixHarness 对应文件。
