# StoryLoop 测试先行

验收套件由 acceptance 角色先写，引擎证明该套件在合同提交时 RED；implement 不能改受保护验收。选一个合同 AC 和已确认的公共验证入口，写项目自己的相关单元测试，确认它因目标行为缺失而红，再写最小实现使其绿。每轮只推进一个可观察行为，回归检查后再做下一轮。

## implement：RED → GREEN

1. 读已批准合同、方案 `touched/creates`、验收 RED 证据和现有测试；只在方案与测试根允许的路径写入。入口缺失或有争议，返回合同／方案澄清，不在实现轮自造入口。
2. 写与已确认入口对应、能约束该 AC 的最小单元测试，实际运行并保存失败命令、失败断言及原因；导入失败、超时、夹具前提失败不算行为 RED。对预先存在且本应保持的行为，先证实 GREEN。
3. 只实现通过这一测试所需的代码，重跑该测试与相关回归；确认绿后才整理代码。若方案或 GREEN 锁禁止新测试，运行已有批准检查并如实说明，不编造 RED。
4. 在交给引擎的 `## Tests First` 中列 AC、测试路径／名称、先红证据和后绿命令结果；引擎的受保护套件、层检查与停点仍是最终门禁。

好测试：用固定输入经公开 CLI／HTTP／公共函数，断言合同给出的具体输出（如 `status == "PASSED"`）。坏测试：只查文件存在、私有函数调用次数、mock 内部协作者，或用生产算法重算 expected。只在外部服务、时间、随机性等系统边界 mock；优先用真实业务链路和独立的期望字面值。

## characterize：先锁不变项

characterize 在实现前为现有文件新建专用测试，断言合同明确要求保持的旧行为；这些测试在当前代码上必须 GREEN，不能把要改变的错误行为锁住。列表或可扩展字段用包含式断言，避免把允许新增的内容锁死；不改已有测试或非测试文件。

技能若与合同、方案、引擎 RED/GREEN、受保护路径或特征化锁冲突，以引擎门禁为准。
