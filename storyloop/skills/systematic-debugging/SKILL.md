# 实现轮系统排错

先读 `payload.failures` 最新完整条目、各层结果、停点 `evidence` 与审查意见 `id`，写清预期、实际、失败签名和来源。不要只凭最后一行报错改代码；先分清实现、验收判据、合同和环境谁拥有问题。

1. 用同一候选状态、命令和输入复现失败；无法稳定复现时记录运行条件与缺失证据，不能宣称已修复。
2. 沿输入、公共入口、调用路径、变更文件与配置缩小范围，提出可证伪的根因假设；用一条有区分度的检查排除竞争假设。区分触发条件、失败表现和根因，引用真实 `path:line`。
3. 若 `payload.mode == root_cause`，先在设计记录 `## Root Cause` 写证据，再做方案允许范围内的最小修复；同一签名无进展时停止盲目重试，按引擎停点处理。
4. 重新运行原失败检查、相关回归和必要的完整层验证，并在 `## Tests First` 记录真实先红后绿结果。审查 `MUST_FIX` 修后还需整体重审；若是 oracle／合同缺陷，走引擎给出的修复或人工入口。

预算、失败归属、自动重试次数、受保护路径和恢复命令均以 StoryLoop 引擎为准；本技能不自行推进状态。

思路参考 HelixHarness 对应文件。
