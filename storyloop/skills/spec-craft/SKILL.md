# Spec Craft：需求共创

## 何时使用

人在对话里提出功能想法，需要先评估价值，再写需求与可验证规格时使用。fix、refactor 和人声明的小改动可以跳过评估，须记录理由。只处理共创；批准、编号和质量检查交给 StoryLoop。

在引擎的 product 角色中，只取下文的事实调查、决策树和入口确认方法；按角色给定 schema 返回产品合同 JSON，不运行 `--view`、不另写需求文档，也不改变 StoryLoop 的批准流程。

## 项目定制

优先运行 `storyloop skills <项目> --view spec-craft`，读取 `.storyloop/skills-view/spec-craft.md` 末尾的“生效配置”节；未生成或无法读取视图时，使用下文的内置默认值。项目里有 `storyloop-custom/spec-craft.toml` 或 `storyloop-custom/spec-craft.user.toml` 时，再按追加的分类、模板节、提问偏好和术语表工作。`question_limit` 可调整每步骤提问上限；定制不能删除或改写内置内容，也不能改变“只能由人判断的事”。

## 五步

| 步骤 | 行动 | 决定者 | 产出 |
|---|---|---|---|
| 0 接入 | 由 StoryLoop 接入流程负责，不在本技能内 | 人确认地图 | 需求地图 |
| 1 评估 | 引导三问，整理回答 | 人决定做、需澄清或放弃 | 评估块 |
| 2 需求 | 按模板起草，猜测标为假设 | 人确认优先级和假设 | 需求文档 |
| 3 规格 | 规则用 EARS，逐条写正例和反例 | 人核对预期结果 | 规格文档 |
| 4 澄清 | 查覆盖地图，逐题提问并写回 | 人回答 | 修订后的文档 |
| 5 交接 | 交给 StoryLoop，见 references/handoff.md | 人批准 | StoryLoop 合同 |

## 工作方式

新合同的每个非 BASE 故事须写 `verification_entries`（`id`、`kind`、`locator`、`observable`、`reason`）。从现有最高层公共入口选择，说明哪些 AC 经该入口可观察；把入口交给人确认后才能批准合同。若没有可信入口或人有异议，留在规格澄清，不让验收或实现阶段另选入口。旧合同无此字段时沿用原流程。

### 需求决策树

1. 先查当前仓库的代码、配置、测试和已批准合同，区分已证实事实、报告者猜测与真正需要人的产品取舍；已有决定先核对是否仍适用。
2. 把目标价值、具体正反例、范围、兼容行为和验证入口排成有依赖的决策树。只问前置答案已确定的 frontier；同一轮一次展示整个 frontier，不把可从仓库查明的事实抛给人。
3. 每题编号，写事实来源（文件 `path:line` 或合同条款）、可选方案、一个具体推荐及主要取舍；未回答的推荐不是批准。若 frontier 超过生效提问上限，合并同一决策的子问题；仍超限就保留草稿并说明缺口，不替人作答。
4. 人回答后更新树并展示新解锁的 frontier。全部决策收敛后，总结共同理解，请人确认例子的预期结果和故事级公共验证入口；确认前不把草稿当已批准合同。

StoryLoop 的合同字段、问题上限、批准停点由引擎决定；本技能不改变这些门禁。

快速方式由 AI 起草整份，供人集中审；引导方式逐节与人共创。轻档和标准档默认快速，重档默认引导。人随时可以切换。先根据 nature 与人的声明估计档位，StoryLoop 分流后只向上补足。

步骤 1 评估、2 需求、3 规格、4 澄清、5 交接中向人提出的问句分别计数，不跨步骤累加；每步默认最多 5 个问题，运行过 `--view` 时以“生效配置”节给出的生效上限为准。步骤 0 接入由 StoryLoop 负责；交接后 StoryLoop 命令行的问答不计入技能。评估固定三问，结论仍由人决定。

## 只能由人判断的事

| 事项 | 在哪一步 | 理由 |
|---|---|---|
| 值不值得做 | 1 评估 | 必要性，大模型几乎总是漏判 |
| 优先级与取舍 | 2 需求 | 业务判断 |
| 假设是否成立 | 2 需求、4 澄清 | 假设本来就是 AI 的猜测 |
| 例子的预期结果对不对 | 3 规格 | 正确性，大模型几乎总是漏判；具体数据让产品看得懂 |
| "改到什么程度算新规则" | 3 规格 | 链路骨架 §5.3 |
| 新模块是否成立 | 2 需求 | 链路骨架 D2 |
