# 正例与反例

每条规则至少一个正例、至少一个反例。**正例**是规则的前提成立时，系统按规则做；对 IF…THEN 规则，异常发生且系统按规则应对就是正例。**反例**是前提不成立，或处在规则边界之外时，系统不按这条规则做，即不误触发。反例不是把正确结果简单改成错误结果。例子的预期结果由人核对，AI 只提出草稿。

每个例子单独标明所属规则、正反（`正反：正例` 或 `正反：反例`）、行类型，以及选择行类型的一句理由。正反与行类型不能互相推出；行类型按“这个例子在旧代码上会不会失败”判断，并沿用 `oracle-craft/references/acceptance-matrix.md` 的验收矩阵，**只引用它，不复制行类型表**：

- 前提成立的正例通常要求新行为，旧代码上应失败；按实际场景和验收矩阵选行类型。例如，无效日期触发 IF…THEN 规则的正例；若旧代码会接受无效日期，或不会给出规则要求的更正提示，完整的 Then 在实现前失败，选 `positive`。`degradation` 只用于依赖失败，不能把输入校验失败归入它。
- 前提不成立的反例要求不误触发，旧代码往往已满足、实现前应通过；按实际场景选 `regression` 或 `non_goal`。例如，已有完成状态的待办不应被逾期标红，可标 `正反：反例`，行类型为 `regression`，理由是旧代码本来不标红。
- 每例必须写出在旧代码上会不会失败的判断和一句理由；证据不够时先查旧代码或请人核对，不把行类型留空，也不根据正反机械套用。

Given 使用具体数据：数字、带引号的文本、日期或 ID；When 写确切动作；Then 写外部可观察的结果。好：“Given 梅玲有待办‘缴费’，到期日 2026-10-20，今天是 2026-10-24，状态未完成；When 她打开列表；Then ‘缴费’标红。”坏：“Given 一个用户有一些待办；When 查看；Then 正确显示。”坏例没有具体数据，也无法让人核对结果。

反例要覆盖边界或异常，如：“Given 同一待办到期日为空；When 梅玲打开列表；Then 它不标红，也不被当作过期。”若“空日期”是否允许尚未确定，先标为假设并请人确认。
