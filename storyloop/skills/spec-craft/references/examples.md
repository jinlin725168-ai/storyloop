# 正例与反例

每条规则至少一个正例、至少一个反例。反例写“规则被违反、或处在规则边界之外时，应当发生什么”，不是把正确结果简单改成错误结果。例子的预期结果由人核对，AI 只提出草稿。

每个例子单独标明所属规则、正反（`正反：正例` 或 `正反：反例`）和行类型。正反与行类型不能互相推出；行类型按“这个例子在旧代码上会不会失败”判断，并沿用 `oracle-craft/references/acceptance-matrix.md` 的验收矩阵，**只引用它，不复制行类型表**：

- 违反规则时系统的应对（IF…THEN）在旧代码上通常尚未实现，例子实现前应当失败；按实际场景选 `degradation`、`unknown_state` 或 `positive`。
- 边界上“不应触发”的情况，旧代码往往已经满足，例子实现前应当通过；按实际场景选 `regression` 或 `non_goal`。例如，已有完成状态的待办不应被逾期标红，可标 `正反：反例`，行类型为 `regression`。
- 拿不准就写“待定”，交给 StoryLoop 的 product 角色按验收矩阵判定；不要根据正反机械套用行类型。

Given 使用具体数据：数字、带引号的文本、日期或 ID；When 写确切动作；Then 写外部可观察的结果。好：“Given 梅玲有待办‘缴费’，到期日 2026-10-20，今天是 2026-10-24，状态未完成；When 她打开列表；Then ‘缴费’标红。”坏：“Given 一个用户有一些待办；When 查看；Then 正确显示。”坏例没有具体数据，也无法让人核对结果。

反例要覆盖边界或异常，如：“Given 同一待办到期日为空；When 梅玲打开列表；Then 它不标红，也不被当作过期。”若“空日期”是否允许尚未确定，先标为假设并请人确认。
